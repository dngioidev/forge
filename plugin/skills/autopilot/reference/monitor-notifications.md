# Monitor notifications — mechanics, thresholds, field evidence

Reference for `plugin/skills/autopilot/SKILL.md` § Monitor notifications (#467 AC-2/AC-3 —
relocated, not deleted). SKILL.md keeps the operational rule for each monitor — the line it
emits and what the loop does with it; this file holds the deeper "why" (poll mechanics,
threshold derivation, field evidence) that a run doesn't need loaded to react correctly, only
to debug or recalibrate.

## `forge-ci` — full mechanics

`plugin/scripts/monitors/ci-watch.mjs` polls the current branch's PR checks and, **only when the rollup transitions**, emits exactly one line. The real shape is `CI <state> on PR #<n> (<branch>)` where `<state>` is one of:

- `pass` — every check is `SUCCESS` / `NEUTRAL` / `SKIPPED`
- `fail` — any check is `FAILURE` / `ERROR` / `CANCELLED` / `TIMED_OUT` / `ACTION_REQUIRED` / `STARTUP_FAILURE`
- `pending` — otherwise (fail-closed on unknowns)

The **merge bar's CI-green requirement surfaces to the loop as the `CI pass` line** — the loop learns of a CI transition from the push instead of inline-polling `gh`, and a `CI fail` line tells it the watched PR went red. *Reacting* to that transition still belongs to the delivery layer, not the loop: the merge bar (`merge.mjs`) and any fix wave execute **inside the delivery subagent**, whose own in-run `--watch` is the authoritative green for the ticket in flight. The `forge-ci` push is strictly the poll-free way for the **loop** to observe the same transitions (including on a parked or other PR). It stays silent until a PR exists for the branch and on any unchanged rollup. A *persistent* poll failure (auth/network) no longer silences it forever (#318): after a few consecutive failed polls it surfaces one `forge-ci error: <reason> (<n> consecutive polls)` line (throttled, not per-poll), then a good poll resets it — a single transient failure stays quiet.

A fourth line is possible (#408): `CI outage-suspected on PR #<n> (<branch>) — stuck queued Xm with no progress (not a real failure; recovery: rebase + repush)`. This fires when every reported check has sat in `QUEUED` status past a generous threshold with zero progress — GitHub's own signature of an Actions platform outage, not a code failure — and is reported **at most once per stuck episode** (it resets the moment the rollup stops being all-queued), never a line per 20s poll. Same rule as the CI-green disclaimer above: this is the poll-free way the **loop** observes the signature; the recovery itself (§ Auto-merge item 4) still runs inside the delivery subagent's own merge-bar check.

## `forge-decisions` — full mechanics

`plugin/scripts/monitors/decisions-watch.mjs` polls `.forge/decisions/` and, the moment an escalation the human answered flips to `status: resolved`, emits one line: `Decision <id> (#<issue>) resolved: <first line of the answer>`. The parked (blocked) ticket named by `#<issue>` re-enters the selection queue on the next iteration (where it runs the full gate pipeline again). A *persistent* fs error (not a missing dir, which is benign) likewise surfaces one throttled `forge-decisions error: <reason> (<n> consecutive polls)` line after a few consecutive failed polls (#318), so a silent fs stall that would keep parked tickets blocked forever becomes visible; a single transient error stays quiet.

## `forge-outbox` — full mechanics

`plugin/scripts/monitors/outbox-watch.mjs` (#414, per the spike `docs/spikes/2026-08-08-github-outbox-design.md`) watches `.forge/autopilot/outbox.json` — the local outbox that lets the loop keep going instead of sitting blocked when GitHub is rate-limited or an Actions outage is underway. Five writes are queue-eligible (`lib/outbox.mjs` `QUEUEABLE_OPS`): `board/comment.mjs` trail comments, `board/move.mjs` board-status moves (the same sub-step `escalate.mjs` reuses for its own `blocked` move), `board/receipt.mjs` merge receipts, `board/log.mjs` delivery-log rows, and `board/digest.mjs` epic digests — each of these `run*` functions tries the live write first (no behavior change while GitHub is reachable) and only queues it, via `lib/outbox.mjs` `attemptOrDefer`, when the failure looks like GitHub being unreachable (`isRateLimited`/`isPlatformOutage`, reused rather than a new signal). Everything else — merges, PR creation, `escalate.mjs`'s own decision comment, `create.mjs`, `reparent.mjs`, and `close.mjs`'s `gh issue close` — stays synchronous with no exceptions; the decision comment in particular calls `upsertMarkedComment` directly rather than through `comment.mjs`, so it is never outbox-aware by construction, not by a special-cased flag. The queue is guarded by its own `.forge/autopilot/outbox.lock` (deliberately separate from any future `run.lock`, #387 — different resource, would cross-block), built on the shared `lib/lock.mjs` exclusive-lockfile helper (`fs.open(path,'wx')`, `{pid,startedAt,hostname}`, PID-liveness + age-staleness reclaim) — the first real implementation of that #387-designed idiom; a future `run.lock` should reuse the same helper. Draining is two composed mechanisms, never a fixed ceiling: **opportunistic** — `attemptOrDefer` tries a drain right after any live outbox-owned write succeeds — and this **background monitor**, which polls, probes reachability with a cheap `gh api rate_limit` call, drains when reachable, and emits a line only on a pending-count transition (`forge-outbox: N item(s) queued (GitHub unreachable)` / `forge-outbox: N item(s) still queued` / `forge-outbox: drained — 0 item(s) queued`). A drain failing for a reason that ISN'T GitHub being down (a real bug — a stale mutation, a malformed queued entry) surfaces immediately as `forge-outbox: drain failed — … (escalation warranted)` — that is the only outbox-driven escalation trigger; an ordinary "still queued, GitHub is down" is never a `blocked` ticket and never routes through `escalate.mjs` (spec §7 reserves that for genuine human decisions). Visibility is read-only against the pending count: `ledger.mjs` `renderReport` gains an optional trailing `outbox: N item(s) still queued …` line, and `board/status.mjs` `computeStatus`/`board_status` gain an analogous `outboxPending` field for the catch-up card — both silent at `0`.

## `forge-agents` — full mechanics + the honest limit (#505)

The delivery brief best-effort writes/refreshes `.forge/agents/<id>.json` at spawn and each phase change, mirroring `ci-watch.mjs`'s `writeCiWatchState` never-fail-the-caller contract. Staleness keys on `lastArtifactAt` (elapsed-time-*without*-a-new-heartbeat), not raw elapsed-since-spawn, mirroring `ci-watch.mjs`'s `queuedSince` — a phase change resets it, so a single long phase never itself reads as a stall the instant it starts.

A heartbeat written *by* the subagent is briefing-dependent, and this run is direct evidence that briefing-dependent safeguards fail (three subagents returned free text despite a bold, escalating warning). The detection that actually diagnosed #457 needed no subagent cooperation at all — harness output-file mtime vs. elapsed wall clock — but no documented, stable, harness-side output/transcript path is discoverable from a monitor process in this repo today, so that cooperation-free approach is not buildable here. A subagent wedged badly enough to never execute its own heartbeat-write call is invisible to `forge-agents` exactly as it was invisible before. If a stable harness-side path becomes discoverable later, it strengthens this mechanism as a second, cooperation-free signal — a possible follow-up, not built now.

**Threshold derivation.** `DEFAULT_STALE_MS` = 60 minutes is 6x the harness's own 600s silent-stall kill floor (a shorter threshold would be redundant: the harness already notifies at 600s, the shape 4 of 5 field-evidence stalls took), while comfortably above every observed legitimate quiet phase in this repo (a full `pnpm verify`, a `gh pr checks --watch` wait, a rebase) so a healthy long-running delivery never false-positives — proven by an injected-clock test (`docs/plans/2026-08-15-505-agent-liveness-detection.md`), not asserted in prose alone.

**Field evidence (2026-08-11/13 run):** four of five stalls were notified (harness stall-kill or a rate-limit kill) and cost minutes; the fifth died silently — no notification at all — and cost 5.3 hours of a 6.6-hour ticket before a human asked for a status check. `forge-agents` closes that fifth shape.
