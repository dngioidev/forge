# Spike — agy's real command-approval semantics: does hook `allow` auto-approve, or just not-block? (#428)

**Date:** 2026-08-12 · **Ticket:** #428 (parent #182) · **Route:** spike (deliverable = this findings doc; no product-source changes — the security finding below is filed separately as #434).

**agy version tested: 1.1.7** (`%LOCALAPPDATA%/agy/bin/agy` on Windows, `agy --version` → `1.1.7`). `docs/guides/cross-gai.md:19,27` and ADR-0007 record the adapter as proven on v1.1.5 — this spike is the first re-verification against a newer build. No version-dependent behaviour was found (the hook I/O contract, decision semantics, and CLI flags below all match what ADR-0007 recorded on v1.1.5), so nothing here invalidates that prior verification, but it should be re-checked again at the next `agy` bump per ADR-0007 "(c)" build-time-confirmation rule.

## The question

`plugin/hooks/agy-deny.mjs:29` and `:42` return `{"decision":"allow"}` as the default for every `run_command` that isn't a denylist hit. ADR-0007 records agy's `PreToolUse` hook decisions across two places — `:37` lists `allow`/`deny`/`ask` in the host-capability matrix, and `:54` adds `force_ask` in the live-verification section — but neither states what each decision actually does to agy's own approval prompt. Two readings inverted each other going in:

1. `allow` = auto-approve, suppresses agy's prompt → forge is already blanket-pre-authorizing every shell command on agy (security finding).
2. `allow` = "this hook has no objection", agy still applies its own approval flow → the allowlist gap is real, fix is selective `allow` with `ask` as the default.

## Findings

### AC.1 — what each decision does to agy's approval prompt

**Source 1 — agy's own shipped hook contract doc**, installed with the exact CLI under test: `~/.gemini/antigravity-cli/builtin/skills/agy-customizations/docs/hooks.md` (§ `PreToolUse` Contract). This is not a blog or a guess — it is the vendor's own reference, shipped inside v1.1.7 itself:

> - `"allow"`: Automatically allow the tool execution.
> - `"deny"`: Hard block the execution immediately.
> - `"ask"`: Prompt the user for permission (respects "Always Allow" cache).
> - `"force_ask"`: Always prompt the user, ignoring cached permissions.

Taken at face value, this settles the question the ADR left open: **`allow` suppresses agy's own approval prompt.** It is not "no objection, agy still asks" — the doc's own verb is "automatically allow."

**Source 2 — empirical confirmation via a scratch plugin** (built for this spike, not part of the forge plugin; lived under a throwaway session scratchpad dir beneath `%LOCALAPPDATA%/Temp/`, outside the forge repo, and is not part of this PR). A project-root `.agents/hooks.json` registered a throwaway `node hooks/pretool.mjs` hook on matcher `"*"` that logs every payload and returns a decision read from a control file, so the same rig could be re-run with each of the four decisions without touching hooks.json between runs. Driven headlessly via `agy --print "<instruct the agent to run one exact command>" --add-dir <scratch> --mode accept-edits` (with and without `--dangerously-skip-permissions`).

The empirical results **reveal a second, independent gate that the docs don't separately name**, and this is the real finding of the spike:

| Hook decision | `--dangerously-skip-permissions` off (headless, no TTY) | `--dangerously-skip-permissions` on |
| --- | --- | --- |
| `allow` | **Still denied.** `jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for, so it was auto-denied. Add an allow-rule under permissions.allow in settings.json (e.g. command(<target>)). Alternatively, re-run with --dangerously-skip-permissions to auto-approve all tools.` The hook fired and logged `{"decision":"allow"}` (confirmed via the invocation log) — agy still refused to run the command. | Command executed. |
| `ask` | Same auto-denied message, verbatim, as `allow`. | *(not tested — no reason to expect a difference; `ask`'s only documented distinction from `allow` is the prompt, and headless has no prompt to show)* |
| `force_ask` | Same auto-denied message, verbatim, as `allow`/`ask`. | *(not tested, same reasoning)* |
| `deny` | **Hard-blocked**, and the agent surfaced our hook's own custom `reason` string verbatim ("scratch hook #428 forced decision=deny") — a materially different, immediate rejection, not the generic headless message above. | *(not tested directly — see reconciliation below; strongly inferred to still block)* |

**Reconciling the two sources — the model that fits all the evidence:** agy has (at least) **two independent gates** a `run_command` call must clear, not one:

1. **The `PreToolUse` hook layer** (forge's `agy-deny.mjs`). `deny` here is absolute and immediate — confirmed directly (headless test above), and this is exactly what ADR-0007's original spike already observed ("the forge Claude denylist even blocked one of my own `rm -rf` commands mid-spike" — the same design, proven again here on the agy side). `allow`/`ask`/`force_ask` all clear *this* layer without objection — the hook layer has nothing more to say once it isn't `deny`.
2. **agy's own native command-permission gate**, separate from the hook. This is the layer `hooks.md`'s "automatically allow the tool execution" / "prompt the user" language is describing — and it is the layer that, per the CLI's own runtime message, has **no path to succeed in headless mode without either `--dangerously-skip-permissions` or a `permissions.allow` grant** (see AC.2), regardless of what the hook said. That is *not* a contradiction of `hooks.md` — headless mode has no prompt to show or suppress, so a documented "allow = skip the prompt" is vacuous there and agy fails closed instead (a deliberate, sane default: no TTY, no rubber stamp).

**What this means for the real, human-facing case (an actual interactive agy session — the scenario the ADR and #429 both care about):** there *is* a prompt to suppress there, and per the vendor's own doc, `allow` suppresses it. This spike could not put a human at an interactive prompt to watch it directly (see "not independently observed" below), but the documented contract is unambiguous, sourced from the shipped CLI itself, and nothing observed contradicts it — the headless-mode auto-deny is a *different, additional* fallback specific to the no-TTY case, not evidence against the documented interactive behavior. **Conclusion: reading 1 is confirmed for interactive agy sessions.** `agy-deny.mjs`'s current default (`allow` for everything non-denylisted) auto-approves every shell command a human would otherwise be asked about, exactly as ADR-0007's fork worried it might. Filed as **#434** (p0 bug) per AC.4, separate from #429.

**Not independently observed (honest gap):** a human physically watching an interactive `agy` session confirm no prompt appears for a hook-`allow`ed command. This spike judged that gap **settled headlessly** rather than escalated it, because: (a) the claim comes from agy's own shipped, version-matched documentation, not a third party; (b) the two-gate model above is internally consistent — it explains every headless observation without requiring the interactive claim to be wrong; (c) `deny`'s hard-block behavior (which the docs describe with the same authority) was independently, empirically confirmed, giving no reason to distrust the doc's description of `allow`. If the owner wants direct visual confirmation anyway, the repro is: `cd` into any workspace with forge's agy hooks installed, run `agy` **interactively** (no `--print`, no `--dangerously-skip-permissions`), and ask it to run any command that isn't on the denylist (e.g. `echo hi`) — per this finding, no permission prompt should appear.

### AC.2 — does agy have a native pre-authorization settings file?

**Yes, partially confirmed.** The CLI's own runtime error (quoted in full above) names it directly: `settings.json`, key `permissions.allow`, entries shaped `command(<target>)` (e.g. `command(echo hello)`) — the same string format as the `permissionOverrides` field `hooks.md` documents for a hook's own output (`["command(npm test)"]`), suggesting one shared permission-string grammar across both surfaces.

- **Confirmed location:** `~/.gemini/antigravity-cli/settings.json` (Windows: `C:\Users\<user>\.gemini\antigravity-cli\settings.json`) — the one `settings.json` that exists anywhere under `~/.gemini` on this machine, and it already holds real user data (`trustedWorkspaces`, a workspace-trust list) confirming it's the live, active global config the CLI reads at startup.
- **Confirmed schema fragment:** `{ "permissions": { "allow": ["command(<exact-target>)", ...] } }` — directly from the CLI's own error text, not inferred.
- **Not confirmed, and explicitly not force-tested:** whether this is global-only or has a project-scoped override. Two plausible project-scoped locations were tried from the scratch workspace (`.agents/settings.json`, `.gemini/settings.json` at the project root) — **neither was honored**; the identical generic auto-deny message reappeared both times. Actually writing the *global* `permissions.allow` entry to confirm the full schema (array vs. single string, glob/wildcard support, per-argument vs. exact-string matching) was **not attempted**: the one attempt to edit `~/.gemini/antigravity-cli/settings.json` for this test was correctly refused by the Claude Code auto-mode safety classifier as a security-weakening write to the operator's real global config, outside the scratch dir this spike was scoped to — and this spike did not retry or work around that refusal, per its own operating rules. This is deliberately left unresolved rather than guessed.
- **No shipped documentation names `permissions.allow` at all** — it surfaced only via the CLI's own runtime error string, not `hooks.md`, `plugins.md`, `json_configs.md`, `mcp_servers.md`, `rules.md`, `skills.md`, or either `antigravity_guide` reference doc (all grepped, zero hits for `permission` outside the hook I/O contract and the unrelated `permissioned-github` skill, which governs `gh`/`git` calls specifically and is a distinct mechanism).
- **A related but distinct surface exists in the Antigravity 2.0 *desktop app*** (`antigravity_guide/references/app.md` § "Agent Settings & Permissions"): a GUI "Command Allowlist / Denylist" and "Permission Grants" concept, with project-level overrides. This is documented for the Electron app, not the headless `agy` CLI, and this spike found no file path or schema for it — it is a UI-configured surface with no discovered on-disk artifact `forge init --host agy` could emit into. Do not conflate it with `permissions.allow` in `settings.json` above; they may or may not be the same underlying mechanism, but only the CLI-facing `settings.json` route is actionable for an unattended adapter.

**Bottom line for AC.2:** the surface exists and its existence changes the design space (a settings-emission path is possible in principle), but it is **global** (not scoped to a project or a forge install), **undocumented beyond a runtime hint**, and its full schema is **unconfirmed** without a live, owner-authorized edit of the real global file. That uncertainty, plus the global blast radius, is itself an input to the recommendation below.

### AC — hook timeout: fails open or closed?

**Fails open.** `emit.mjs:126,129` sets `timeout: 10` (seconds) on both hooks. The scratch hook was made to sleep 60 seconds (`decision.txt=allow`, `sleep-ms.txt=60000`) while `hooks.json`'s configured timeout stayed at 10. The whole `agy --print` round trip (model calls + tool call) completed in ~29 seconds — well short of the 60-second sleep — **and the command executed successfully**. The hook's own log line proving it reached completion (`wrote: ...`) never appeared, meaning agy stopped waiting on the hook well before the 60-second sleep finished and proceeded as if the (never-received) decision were `allow`. This matches `agy-deny.mjs`'s own in-script fail-open catch (`:42`, for a script-internal error) but is a **separate, host-level fail-open** — agy itself defaults to allow when a hook doesn't answer in time, independent of anything the hook script does. **Consequence for #429:** a hook that is slow or hangs (system load, a bug, a transient Node startup stall) silently degrades to the least safe outcome, not the safest one. Any allowlist design must keep the hook fast and simple enough that 10s is never a realistic ceiling, and should not rely on the timeout as a safety backstop in either direction.

### AC — does agy apply hooks to non-shell tools?

**Yes, when the matcher allows it — this is forge's own scoping choice, not an agy limitation.** With the scratch hook's matcher set to `"*"` (matches every tool) and `decision.txt=deny`, asking agy to create a file via its native file-write tool (not `run_command`) was blocked with the exact same hard-block message, and the invocation log recorded `"name":"write_to_file"`. agy's hook matcher supports arbitrary tool-name regexes (`hooks.md` § "The Matcher": `"*"`, an exact name, `a|b`, or a prefix pattern) — `run_command\|write_to_file` would cover both with zero new code. **forge's own `hooks.json` matcher is `run_command` only** (`emit.mjs:126,129`) — a deliberate scope, confirmed here to be a choice forge made, not something agy forces. Whether that scope should widen (covering file writes/edits the way the Claude host's own permission model does) is a design question for #429, not something this spike resolves.

## Recommendation (AC.3)

**Hook-mediated allowlist: flip `agy-deny.mjs`'s default from `allow` to `ask`, return `allow` only for a known-good command set.** Reasons, weighing the two options head to head:

- **The security posture of today's default, assessed plainly:** unsafe. Reading 1 is confirmed for interactive sessions (AC.1) — every non-denylisted shell command an agy-hosted forge session runs today is silently pre-approved, with zero visibility to whoever is watching the session. This is worse than "missing a feature"; it's a standing exposure, hence #434 filed as p0 today rather than folded into #429's backlog priority.
- **Why hook-mediated over native-settings-file, for the *fix*:** the native `permissions.allow` surface (AC.2) is real but comes with three open costs a hook doesn't have: (a) it is **global** (per-user-account, not per-repo) — an emitted grant list would leak across every project the operator has open in agy, a much larger blast radius than a repo-local hook; (b) its **schema is unconfirmed** beyond one example string, and confirming it safely needs an owner-authorized edit of the operator's real config, not something `forge init --host agy` should attempt blind; (c) it appears to support only **exact command strings** (`command(<target>)`, one example given, no documented wildcard/pattern syntax) — a hook can inspect the live command text and apply real logic (prefix match, argument-aware rules, the same style `denylist.mjs`'s `check()` already uses), which is a better fit for "known-good command set" than a static pre-declared string list would be to maintain. A hook is also **already the wired mechanism** — `agy-deny.mjs` exists, is installed, and this is a smaller, lower-risk change than introducing a second emission path.
- **Why `ask` (not `force_ask`) as the new unrecognized-command default:** `hooks.md` distinguishes them precisely: `ask` "respects the 'Always Allow' cache" (a human who's already approved a command in-session isn't re-asked every time), `force_ask` never does. `ask` is the same trust model Claude Code's own `permissions.allow`/interactive-prompt combination already gives forge on the Claude host — matching that bar (not exceeding it, not falling short) is the right default per ADR-0007's stated full-parity goal.
- **The timeout finding is an implementation constraint, not a design-direction input:** whichever direction #429 takes, the hook script must stay trivially fast (it already is — a synchronous denylist regex check) so the 10-second, fail-open timeout is never realistically hit.
- **A future, secondary enhancement worth flagging for #429 to consider, not adopt outright:** widening the hook matcher beyond `run_command` (AC — non-shell tools, above) so file writes/edits get the same treatment shell commands do — the current `run_command`-only matcher means a would-be allowlist covers only half the mutation surface a human on the Claude host would see gated. This spike surfaces it; #429 should decide whether it's in scope or a follow-up.
