# Spike — runner-tool failures + machine monitoring research (live vs. file-report split) (#383)

**Date:** 2026-08-05 · **Ticket:** #383 (parent #182) · **Route:** spike (deliverable = this findings doc; no code changed).

## Question

Ticket #383 reports three problems from hands-on runner-tool use, post-OSS-flip (#209/#375): (1) `runner-check` reports NOT READY, (2) the cockpit's usage panel looks frozen, (3) there's "no monitor for the current machine." For each: is it a bug, a UX/messaging fix, or new scope? And, separately: what should local machine/service monitoring actually cover, and how should "live monitoring" relate to "viewing reports built from files"?

## A. The three problems, classified

### 1. `runner-check` NOT READY — UX/messaging fix, with a residual conceptual gap that is new scope

Reproduced: `plugin/scripts/runner/check.mjs` `runCheck()` correctly **FAILs** `private-repo` (lines 161-169, since forge is now public — `vis.isPrivate` is `false`) and correctly **FAILs** `runner-online`/`runner-online-windows` (lines 179-193, via `probeRunnerOnline` in `plugin/scripts/lib/runner-checks.mjs` lines 61-82, `offlineLevel: 'fail'`) because both registered runners are genuinely offline. `serviceTargetResults` (`runner-checks.mjs` lines 199-209) also correctly **warns** that a service is running but targets 0-online repos.

None of this is wrong — every check is reporting ground truth. The problem is that `runCheck` is a single **adoption-readiness** verdict (`ready = failed.length === 0`, line 219), so a repo that legitimately shouldn't use the runner anymore (public, ADR-0005 decision 3) collapses into the same NOT READY output as a repo that wants the runner but it's broken. There is no distinction in the tool's output shape between "this repo is correctly excluded" and "the runner is unhealthy for a repo that wants it" — both produce `✗ private-repo` / `✗ runner-online` lines and a `NOT READY — N blocker(s)` verdict.

**Classification:** mostly (b) — a UX/messaging fix. The individual check outcomes are correct; what's missing is a repo-aware framing (e.g. "this repo doesn't want the runner anymore; unrelated to whether the runner machine itself is healthy") on the `private-repo` fail line, and arguably suppressing/downgrading the `runner-online` fail once `private-repo` has already failed (querying online status for a repo that's explicitly disqualified is redundant noise). That's a same-file wording/short-circuit change, not new architecture. But fully resolving "is my machine's shared runner service healthy" (as opposed to "is this repo permitted to adopt it") is a different question than `runner-check` is built to answer — see problem 3; a message tweak here doesn't invent that view, it just stops it from *looking* like the tool itself is broken.

### 2. Usage panel looks frozen — a bug fix, but not a naive one-liner

Confirmed: `tools/runner-ui/forge_cockpit/web/app.mjs` `boot()` (lines 427-434) wires `setInterval(loadFleet, 5000)` and `setInterval(pollHealth, 15000)`, but `loadUsage()` (line 182) is only invoked from `switchMode('usage')` (line 387) — no interval. Sitting on the tab, nothing re-fetches.

The catch: `loadUsage()` hits `GET /api/usage` (`server.py` line 308), which calls `collect_usage()` → `iter_transcript_paths()` + `parse_transcript()` (`usage.py` lines 260-361) — a **full re-scan of every `*.jsonl` transcript under `~/.claude/projects/**`** on every call, streamed line-by-line with no caching or incremental read. That's a fundamentally heavier request than `loadFleet`'s shell-outs (`sc query`/`systemctl`/`docker ps`, bounded to a handful of `forge-runner*` entries) or `pollHealth`'s liveness ping. Copy-pasting the fleet pattern (`setInterval(loadUsage, 5000)`) would re-parse a growing multi-session history every 5 seconds while the tab is open — wasteful today, and it gets slower as `~/.claude/projects/` accumulates transcripts over the life of the machine.

**Classification:** (a) bug fix, but the fix should be usage-shaped, not fleet-shaped: gate the interval on `currentMode === 'usage'` (only run while the tab is visible — already true of the one-shot call, just needs a `setInterval`/`clearInterval` pair on tab switch) and use a materially longer period than fleet's 5s (cost/token totals change on the timescale of Claude Code turns, not seconds — 30-60s is closer to how fast the data actually moves). This is the "polling-cost tradeoff" the ticket asked to check for: it's real, and it's why this isn't a pure one-line copy of the existing `setInterval` calls.

### 3. No machine monitoring — genuinely new scope

Confirmed by reading `discovery.py` (full file) and `control.py` (header + `ACTIONS`): the cockpit's data layer enumerates service/container **registration state** only — `sc query` (Windows, `discovery.py` lines 157-198), `systemctl --user list-units` (Linux, lines 204-257), `docker ps` (lines 263-318), cross-referenced against `gh api .../actions/runners` for online/offline counts (lines 324-359) — and `control.py` only starts/stops/restarts those same services. There is no code path anywhere in `tools/runner-ui/forge_cockpit/` that samples CPU, memory, disk, or network, tracks a restart/crash count, or reads a job/queue depth. This is not a bug or a UX gap — it's territory the cockpit has never covered. See §B for what it should cover and how.

## B. What "monitor the current machine" should mean, and how

### What to track

For a box running (or that used to run, for this repo) a self-hosted CI runner service plus the forge cockpit, three tiers of signal are the standard local-monitoring shape:

1. **Resource metrics** — CPU%, memory (used/available), disk (free space on the runner's work volume), and optionally network I/O. Point-in-time or short-window sampling, not a full time-series database.
2. **Service health beyond binary up/down** — restart count, crash-looping (rapid restart cycling), time-since-last-restart, last-exit reason. `discovery.py`'s `service_state` today is a single snapshot word (`running`/`stopped`/`exited`/...); it has no memory of *how* a service got there or how often.
3. **Job/queue backlog** — for a GitHub-Actions-backed runner specifically, whether jobs are queued and waiting (as distinct from "is the runner online").

### How to get it cheaply, cross-platform, and consistent with forge's existing constraints

**Resource metrics — use `psutil`, which is already paid for.** `tools/runner-ui/pyproject.toml` line 9 declares `psutil>=5.9` (locked at `psutil==7.2.2` in `uv.lock`), and it is already classified `BSD-3-Clause` in the license gate's curated Python map (`plugin/scripts/gates/license.mjs` line 73, inside `PYTHON_LICENSES`, itself within the default permissive allowlist at lines 31-34). It survived the #355 PySide6/Qt purge — it was declared under ADR-0006 Decision 3 for the (now-retired) desktop cockpit's "process/resource monitoring," and nobody has removed it from `pyproject.toml` since. **However, `grep -r "import psutil" tools/runner-ui` returns nothing** — it is currently an unused dependency. This is the single most load-bearing finding of this spike: **CPU/mem/disk sampling can be added with zero new dependency, zero new license-gate work, and zero new install-time cost** — the license check, the `uv.lock` pin, and the allowlist entry all already exist; someone only has to write the code that imports it. `psutil` is also genuinely cross-platform (Windows/Linux/macOS, one API), which fits the shell-out-only control strategy's spirit without literally shelling out for every metric — it wraps the platform syscalls itself rather than forge having to parse `Get-Counter`/`/proc` output by hand.

**Service restart/crash history — OS-native signals exist on Linux, not on Windows/NSSM, so this needs a design call.** `systemctl show <unit> -p NRestarts,ActiveState,SubState,ActiveEnterTimestamp` exposes a restart counter and state history natively — a **free**, no-new-dependency signal for the systemd leg, reachable exactly the way `discovery.py` already reaches systemd (`wsl.exe -- systemctl --user ...`). Windows NSSM has no equivalent queryable restart counter (`sc query`/`Get-Service` expose only current state, not history), so getting a comparable signal there means the cockpit tracking state transitions itself across polls and persisting them locally (see §C) — an asymmetry between the two OS legs that a follow-up ticket needs to resolve explicitly, not paper over.

**Job/queue backlog — reuse the existing `gh api` pattern, add one more call.** `discovery.py`'s `_query_repo_runners` (lines 340-359) already calls `gh api repos/{owner}/{repo}/actions/runners`; a queued-jobs count is the same shape one call away: `gh api repos/{owner}/{repo}/actions/runs?status=queued`. No new tooling class — it's the identical `gh_runner` shell-out seam `cross_reference_online` already uses.

**Rejected: a node_exporter/Prometheus-style local collector.** Node Exporter is designed to run as a long-lived daemon that a separate Prometheus server *scrapes* over HTTP/9100 (per Prometheus's own docs and multiple guides reviewed below) — it assumes a pull-based observability stack that forge does not have and has no reason to stand up for a single-machine cockpit. Adopting it would mean installing and running a second background process, building forge's own scraper against its `/metrics` endpoint anyway (since there's no Prometheus server to do that job), and parsing Prometheus's text-exposition format — strictly more moving parts than calling `psutil.cpu_percent()`/`psutil.virtual_memory()`/`psutil.disk_usage()` in-process from the FastAPI backend forge already runs. Node Exporter is the right tool when *many* hosts feed *one* aggregator; forge's cockpit is a single-box, single-viewer tool where the already-declared `psutil` dependency is the correct-weight answer.

### The `private-repo`/`runner-online` UX gap (tying back to problem 1)

The tool needs to keep two questions separate rather than collapsing them into one verdict:
- **"Is this repo allowed to adopt the local runner?"** — `runner-check`'s job today. `private-repo` failing on a public repo is correct and must keep failing this verdict (ADR-0005 decision 3, fork-PR RCE).
- **"Is the runner machine/service itself healthy?"** — a question that stays relevant even after a repo answers "no" to the first (the box still serves `dngioidev/iomanage`, per the ticket). Nothing today answers this question independent of a specific repo's adoption check — the cockpit's fleet view (`discovery.py`) comes closest (it lists all `forge-runner-*` services regardless of which repo asks), but it still only reports registration state, not health depth (§B above).

Concretely: `runner-check`'s `private-repo` fail message should say the repo is *correctly excluded*, not imply brokenness, and the tool should note the machine/service may still matter for other repos (pointing at the cockpit). This is the message-level part of problem 1's fix; the machine-health-independent-of-repo view is properly problem 3's scope.

## C. Live-monitor vs. report-from-files — where the split already lives, and where it should go

The ticket asks where a live/session-scoped monitor should sit relative to a historical/file-based report viewer. Reading `logs.py` and `usage.py` first, as instructed, shows **the split already exists in the codebase — but as a data-source axis, not a UI-tab axis**:

- **`discovery.py`/`control.py` are live-only by construction.** Every call re-shells-out (`sc query`, `systemctl --user list-units`, `docker ps`, `gh api`) and returns a fresh snapshot; there is no persistence layer. This is what the cockpit's 5s/15s polling (`app.mjs` lines 432-433) is built for, and it stops working the instant the backend/service is down — by design, since "is it online right now" is inherently a live question.
- **`logs.py` is already a report-from-files reader.** `read_logs` (lines 56-80) reads static files — `service.out.log`/`service.err.log` for NSSM (`_read_windows_logs`), or `journalctl --user -u <unit>` for systemd (`_read_journal`, which itself reads systemd's own persisted journal, not a live stream — `journalctl` without `-f` returns a bounded tail). It returns a snapshot on each call; the cockpit's UI re-triggers it on tab-switch/selection (`app.mjs` `loadLogs`, lines 273-305), not on an interval. It already tolerates the underlying service being stopped (NSSM's log files and systemd's journal both persist past a service's own lifetime).
- **`usage.py` is already a report-from-files reader too**, and the most explicitly file-grounded of the three: `collect_usage`/`iter_transcript_paths` (lines 260-361) read `~/.claude/projects/**/*.jsonl` directly off disk — no live process, no service dependency at all. It works identically whether the runner is online, offline, or was never installed.

So the codebase's real axis today is: **discovery/control = live shell-out probes; logs/usage = static file reads**, both currently exposed through the *same* FastAPI backend and the *same* mode-bar UI (`app.mjs` `MODES`/`TABS`, lines 374-409). The report-vs-live distinction is not a missing architecture — it's an existing pattern that a new machine-monitoring feature should extend, not reinvent.

**Recommendation for where new monitoring data should live:**

1. **Don't build a second backend, CLI, or "shared abstract data model."** The existing FastAPI app already serves both live (`/api/fleet`, `/api/control`) and file-based (`/api/logs`, `/api/usage`) endpoints side by side, behind the same loopback/token hardening (`security.py`, #352) and the same static frontend. A separate CLI or service would duplicate that auth/serving layer for no benefit — the cockpit already *is* "the local tool that reads files and shows them," which is exactly what a report viewer needs.
2. **Live metrics (CPU/mem/disk "right now") join the existing live pattern**: a new `/api/machine` (or similar) endpoint, sampled with `psutil` in-process on each request, polled by the UI on an interval analogous to `loadFleet` — genuinely session-scoped, genuinely requires the backend running, exactly like fleet/control today.
3. **Historical data (restart/crash history, past resource trends, past job outcomes) needs a persistence step logs.py/usage.py don't need to invent, because they lean on data something else already persists** (NSSM's log files, systemd's journal, Claude Code's own transcript writer). Machine-health history has no equivalent existing writer — nothing today appends restart events or resource samples to a file the way Claude Code appends to its JSONL transcripts. **This is the one place this spike surfaces a real open design question rather than a grounded answer**: does forge want a small always-on background sampler (its own lightweight, `psutil`-based process or a thread inside a long-running cockpit) that appends snapshots to a local file on an interval — so a report survives even when nobody has the cockpit UI open — or is "report" scoped more narrowly to "whatever was captured while the cockpit happened to be running"? Either answer is buildable on the existing pattern (a new `/api/reports`-style endpoint reading whatever file the sampler writes, mirroring `read_logs`), but *which* sampler design is a product decision, not something this research should invent.
4. **UI placement**: extend the existing Usage/Term/Logs mode bar rather than inventing new top-level chrome — a `Machine`/`Health` tab sits naturally alongside the other three (`app.mjs` `MODES`/`TABS` already generalizes to a fourth entry with no structural change), showing live metrics up top and a historical section (once the persistence question above is resolved) below, the same layout shape the Usage tab already uses for "today's stats" + "last 14 days chart."

## Follow-up tickets for the owner to decide on (not created here)

1. **`runner-check` messaging** — repo-aware framing for the `private-repo` fail (distinguish "this repo is correctly excluded" from "the runner is broken"); consider short-circuiting/downgrading `runner-online` once `private-repo` has already failed. Small, `plugin/scripts/runner/check.mjs` + `plugin/scripts/lib/runner-checks.mjs` only.
2. **`app.mjs` `loadUsage()` interval** — add a visibility-gated interval (start on `switchMode('usage')`, clear on leaving) at a materially longer period than fleet's 5s (e.g. 30-60s), given the full-transcript-rescan cost documented in §A.2. Small, `app.mjs` only.
3. **Machine resource metrics** — new `psutil`-backed sampling (CPU/mem/disk, possibly network) exposed via a new endpoint + cockpit panel. Genuinely new scope; the dependency is already in place (§B) so this is mostly design + implementation, not a dependency-approval cycle.
4. **Service restart/crash-loop history** — needs an explicit design decision on the Windows/NSSM vs. Linux/systemd asymmetry (systemd exposes `NRestarts` natively; Windows needs the cockpit to track transitions itself) and a persistence approach. Flag as an open question for the owner before scoping.
5. **Report-viewing surface for historical machine data** — a new read-only endpoint (e.g. `/api/reports`) plus a cockpit mode, following the `logs.py`/`usage.py` file-reading pattern once (4)'s persistence question is answered. Depends on 3 and 4.
6. **Optional: GitHub Actions queue-depth** — `gh api repos/{owner}/{repo}/actions/runs?status=queued`, same shell-out seam `discovery.py`'s `cross_reference_online` already uses. Small, could ride along with 3.

## Open question for the owner

Item 4 above is the one place this spike could not produce a grounded, single recommendation: **should forge run a small always-on background sampler that persists machine-health snapshots to a local file independent of whether the cockpit UI is open**, or is "report" meant to cover only what was captured during active cockpit sessions? This changes the shape of follow-up ticket 3/4/5 materially (a background daemon is new standing infrastructure; a cockpit-session-scoped capture is not) and is a product call, not something groundable from the existing code.
