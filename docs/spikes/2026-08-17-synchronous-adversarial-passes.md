# Spike — synchronous adversarial passes vs. the spawn-and-await stall (#475, follow-up to #464)

**Date:** 2026-08-17 · **Ticket:** #475 (parent #183) · **Route:** spike (deliverable = this findings doc; **no change to `forge:deliver`, `forge:execute-agents`, or the autopilot delivery brief** — this branch does not touch those files).

## The question

Instead of detecting and recovering from the return-then-resume stall (#464, and its auto-recovery follow-up #474), remove the reason to wait: have delivery subagents run their adversarial passes (`forge:reviewer`, `forge:security`) **synchronously in-run** rather than spawning nested review subagents and returning to await their verdicts. Evaluate honestly: what spawn-and-await buys, what synchronous passes would cost/save, whether synchronous passes would have prevented all four stalls #464 catalogued or only the specific failure mode it patches, and a recommendation surfaced as a decision point — not an autonomous change to the delivery contract.

## Grounding methodology

Every claim below is checked against real repo state: `gh issue view`/`gh pr view` on the tickets and PRs named, `git log` for the merged commits, and the shipped skill text in `plugin/skills/execute-agents/SKILL.md` and `plugin/skills/autopilot/SKILL.md`. Six stalls are in evidence: #464's original four (#429, #437, #446, #460, all closed) and two that occurred in this same run before #474 shipped (#469, #472, both merged — PR #536 and PR #539). #474 itself shipped in this run as PR #540 (`55004b3`), closing #474. Nothing here is assumed from the ticket's own framing without independent confirmation — where a claim in the ticket body needed checking (e.g. "#469's security pass ultimately ran synchronously in-context and still returned a clean, useful verdict"), it was verified against that PR's own trail comment.

## 1. What "spawn-and-await" actually is

Crazy-mode autopilot nests two levels: the orchestrator loop spawns one **delivery subagent** per ticket (this doc is being produced by exactly such a subagent, for #475), and that delivery subagent, at ship time, spawns `forge:reviewer` + `forge:security` as further nested subagents (`plugin/skills/execute-agents/SKILL.md`: *"Spawn `reviewer` + `security` on the full branch diff; fix waves (fresh `implementer` spawns) until both come back clean."*). `execute-agents`'s own rule — *"Never let a subagent drive the loop or spawn its own subagents"* — governs the **role** subagents (reviewer, implementer, etc.) not spawning further; it does not forbid the delivery subagent's one level of nesting for adversarial review, which is the existing, designed shape.

Three distinct behaviors get conflated under "spawn-and-await," and the distinction matters for what #475 is actually proposing to remove:

- **(a) Spawn, then block in-turn.** Issue `reviewer` and `security` as parallel calls, wait for both to return within the *same* delivery-agent turn, never handing control back to the orchestrator in the meantime. This is what `autopilot/SKILL.md`'s § Orchestration already mandates (*"the subagent must therefore watch CI to conclusion in-run itself... never return on the assumption it will be re-spawned"* — the same discipline applies to review verdicts) and is not itself a stall.
- **(b) Spawn, then return awaiting a notification.** The delivery agent spawns the nested reviewer/security agents and then **returns** a non-terminal, waiting-shaped report anyway, discarding its own context. The nested agents' verdicts land on the orchestrator as task notifications, not on the now-gone subagent. This is the actual observed failure in all six stalls, and it is a **discipline failure of (a)**, not evidence that (a) is unworkable — the brief already told every stalling agent not to do this, and it still happened six times (#464's own words: *"The skill has a dedicated section forbidding this... It still happened four times... the agent spawns a review subagent, correctly recognises it must not proceed without the verdict, and then reaches for the only shape it knows for 'wait' — returning."*).
- **(c) No spawn at all.** The delivery agent performs the reviewer/security role itself, inline, in its own context — no fresh subagent, no isolation. This is what #475 is actually asking to evaluate ("synchronously in-run... rather than spawning nested review subagents"), and it is a structurally different proposal from simply disciplining (b) back into (a).

This doc evaluates **(c) vs. (a)**, since (a) is the documented, intended contract and (b) is a bug in following it, not an argument against it. #474 is itself a hardening of the (b)→(a) discipline gap: it doesn't touch whether review is nested, only what happens when a subagent fails to hold the (a) discipline.

## 2. What spawn-and-await (a) buys

- **Parallelism.** Reviewer and security run as two concurrent passes over the same diff rather than one context doing both roles serially. `execute-agents`'s ship step spawns them together explicitly for this reason.
- **Context isolation — the strongest argument, backed by fresh evidence this run.** A reviewer that shares the implementer's context inherits its blind spots and its incentive to see the diff as already-correct. Concrete, verified instances from this run alone:
  - **#472** (PR #539): the nested reviewer, with no stake in the diff having "already been written correctly," caught that the delivering agent's own newly-added code comment overclaimed an invariant that didn't actually hold across all cases — the delivering agent's own trail records it as a genuine correction prompted by the review, not self-caught (*"Corrected one legitimate in-scope issue this surfaced: my own new comment had overclaimed an alignment invariant..."*).
  - **#448** (PR #534): four full adversarial rounds were needed to converge, and three of them surfaced a **different, real critical/high finding** the implementer had not caught in the round before — including a quadratic-backtracking ReDoS (8.7s against a 500ms budget) in round 2, found by `forge:security` independently re-deriving the detection logic from scratch, not by re-reading the implementer's own reasoning.
  - **#449 and #470**: both were halted and escalated to the human specifically because a **nested** adversarial pass (not the delivering agent) found a residual architectural gap the delivering agent's own narrower fix didn't cover. #470's own escalation names the *same* meta-pattern #449's escalation had already named — evidence that this is a recurring blind spot in how the fix is approached, which two independent fresh reviewer contexts each caught, on two different tickets touching the same file.
  - None of these four is a case a same-context self-review is well positioned to reproduce: in each, the finding was precisely the thing the writer's own framing had missed *because* it wrote the diff that way.

## 3. What synchronous (c) would cost and save

**Costs:**
- Loses the context-isolation value in §2 — not hypothetical, demonstrated four separate times this run.
- **Burns the delivery agent's own session budget for review on top of implementation, in the same context — and this is not a free-floating theoretical cost.** #437's stall (one of #464's original four) was **compounded by a session usage-limit kill** that took out the delivery agent and its reviewer mid-flight (#464's own body: *"a session usage limit killed the delivery agent and its reviewer mid-flight... `autopilot.sessionPauseThresholdPct` being unset... is why the run was hard-cut rather than pausing at a ticket boundary"*). Stacking a full adversarial review pass into the same context that already carries the entire implementation trace works directly against what `docs/spikes/2026-08-05-session-window-detection.md` (#378) was chartered to mitigate — it makes hitting that limit mid-ticket *more* likely, not less.
- Loses the reviewer/security concurrency — one context can only run one pass at a time, so two roles done in-context is strictly more turns than two parallel spawns, though the marginal cost is bounded (one diff read, two structured passes, not a doubling of total work).
- **No evidence yet that self-review-in-context catches what nested review catches.** The one concrete data point this run offers for "synchronous" — #469's security pass, run inline against a diff the same agent had just written — returned a clean verdict, but against a **documentation-only** diff with no logic to miss, which is a low bar. Nothing in the evidence base shows a same-context pass catching a critical the same agent had already written past once, which is the exact shape §2's four examples demonstrate nested review catching.
- **The isolation argument has a sharper, security-specific edge beyond honest blind spots.** §2's four examples are all about an implementer's own *honest* framing missing something. `forge:security`'s stated brief is broader than that: it exists to treat the diff as potentially **hostile**, not merely imperfect — a ticket body or an upstream input crafted to steer the reviewing agent is a threat model a same-context pass structurally cannot defend against the way a fresh subagent spawn can, because anything that already influenced the delivering agent's context can just as easily influence a same-context "security" self-check it performs afterward. No instance of this in the evidence base — this run's tickets are all internally authored — but it is a real, not hypothetical, category of cost that a synchronous default would take on for every future ticket, independent of whether the implementer's own reasoning was otherwise sound.

**Saves:**
- Removes exactly one source of "return-and-wait" temptation from the delivery agent's task list (see §4 for how much of the actual stall surface that is).
- Removes the extra subagent-spawn latency/orchestration overhead for reviewer/security specifically.

## 4. Would synchronous passes have prevented the stalls?

All six observed stalls — #429, #437, #446, #460 (#464's original four, all closed) and #469, #472 (this run, both merged) — share **one mechanical shape**: the delivery subagent spawned nested `forge:reviewer`/`forge:security` and then returned a waiting-shaped report instead of blocking in-turn. Since removing the nested spawn removes the exact thing being waited on in every one of these six cases, **yes — synchronous passes (c) would have prevented all six**, not just the narrower slice #464/#474 target.

But that answer needs a caveat #464's own diagnosis already states plainly: *"the agent... reaches for the only shape it knows for 'wait' — returning."* That is a description of a **general model-behavior tendency around any pending async work**, not something specific to reviewer/security. The delivery pipeline has other nested-spawn points with the identical structural shape — most notably `execute-agents`'s own **per-task `reviewer` spawn** (step 4: *"spawn `reviewer`... on the task diff"*, before ship, separate from the full-branch ship-time pass) and `design-reviewer` on UI tickets. #475's proposal does not touch either of those. So:

- Synchronous passes close **100% of the failure instances observed to date** (all six happen to be ship-time reviewer/security waits).
- Synchronous passes close **none of the general tendency** #464 names as the root cause — they remove one spawn point's worth of "things to wait on," not the behavior of returning instead of blocking. The same shape remains structurally possible at every other nested-spawn point in the pipeline, untested so far only because it hasn't been observed yet, not because it's been ruled out.
- **#474 is not actually role-general, and an earlier draft of this section overstated that it was — worth correcting rather than quietly restating.** `matchHeldVerdicts()` (`plugin/scripts/autopilot/watchdog.mjs:266`) is typed and implemented against exactly two roles: `heldVerdicts` is `Array<{issue, role: ('reviewer'|'security'), ...}>`, and the free-text classifier is two hardcoded patterns, `SECURITY_RE = /\bsecurity\b/i` and `REVIEWER_RE = /\breviewer\b/i` (`watchdog.mjs:215,217`). #469 and #472 are not evidence of generalizing to a *different* role — both are the same two roles the mechanism was built for, differing only in how the free text names them (one role named explicitly vs. "both" implied). So #474 reliably covers the ship-time reviewer/security wait (§4's six stalls) but would need real, untested extension work — a new role pattern, a wider `heldVerdicts` type — before it could be assumed to also cover a per-task-reviewer or design-reviewer stall. That's a smaller claim than "#474 already generalizes further than removing one spawn point would," and it changes §6's recommendation only at the margin: the case for keeping spawn-and-await still stands on §2's evidence alone, but the follow-up named in option 1 below (verifying #474 extends to other spawn points) is now clearly *new work*, not confirmation of something already true.

## 5. The effect of #474 having already landed (this run)

#474 shipped and merged as PR #540 (`55004b3`) earlier in this same run, after a three-round adversarial fix wave — the free-text role/negation parsing needed to match "what the report says it's waiting on" against "verdicts the loop holds" produced two real false-relay bugs before converging (round 1: false relays on bare word collisions and unhandled negation; round 2: a negation-cue list missing eight "the wait is over" completion phrasings). That fix wave is a real, non-zero maintenance cost — every new way an agent might phrase "I'm waiting" is a potential future false-relay or missed-relay case for this heuristic text matcher.

But weighed against what it bought: for every one of the six observed shapes (and, per §4, plausibly others sharing the same report structure), the orchestrator now **auto-resumes the stalled subagent from its own transcript, with context intact, no human needed.** The residual cost of a stall is no longer "ticket parks until a human notices" — it's one extra relay round-trip. That reframes the question #475 asks. It is no longer "stall vs. no stall." It is: **is the now-small residual cost of an occasional relayed stall, plus #474's bounded and already-hardened parsing fragility, worth more than giving up the demonstrated adversarial-independence value in §2** — a value that has direct, fresh evidence (#448, #449, #470, #472) that is *stronger* than what #464 had when this ticket was filed.

## 6. Recommendation

**Keep spawn-and-await (a) as the default for `forge:reviewer`/`forge:security`. Do not adopt synchronous in-context adversarial passes as the general delivery contract.**

Reasoning, weighed rather than asserted:
- The cost side of spawn-and-await (the stall) is now small and mechanically bounded by #474, which already shipped and reliably covers the two roles it was built for (§5) — extending it further is plausible but not yet proven.
- The benefit side (context isolation) is not hypothetical — this run alone produced four fresh, concrete instances (§2) of nested review catching what the delivering agent's own context had missed, including one case (#470) explicitly showing the same blind spot recurring across two different tickets, which same-context self-review has no mechanism to correct for.
- Synchronous passes would have prevented every stall observed **so far**, but only because every stall observed so far happens to share one spawn point; the underlying return-then-resume tendency #464 diagnosed is not specific to reviewer/security and is not fixed by removing just that one spawn.
- The one already-adopted synchronous case in this run's own practice — falling back to an in-context pass when a spawn is genuinely unrecoverable (this ticket's own delivery brief authorizes exactly that; #469 used it, on a documentation-only diff) — is worth **keeping as a fallback**, not promoting to the default. It is the lowest-risk place synchronous review already lives today.

**This is a decision for the human, not this ticket's to make unilaterally** (per #475's own scoping). Options, laid out for the escalation:

1. **Keep spawn-and-await + #474 as the standing mitigation (recommended).** No delivery-contract change. Optionally file a narrow follow-up verifying #474's matcher generalizes to the per-task `reviewer` and `design-reviewer` spawn points, since nothing currently confirms that beyond structural similarity.
2. **Adopt synchronous passes as the default**, accepting the demonstrated loss of adversarial independence (§2) and the added session-budget pressure (§3), in exchange for removing the stall's raw material entirely rather than relying on #474's relay to recover it.
3. **Hybrid**: synchronous review for low-risk ticket kinds only (e.g. `chore`/`docs`-classified tickets, where #469's clean synchronous pass is the closest existing precedent), nested spawn-and-await retained for `code`/`feature`/`bug`/`spike-with-diff` kinds where §2's evidence concentrates. This would need its own scoping ticket if chosen — not implemented here.
