# Spike — characterize + detect the harness classifier's mid-run merge denial (#398)

**Date:** 2026-08-08 · **Ticket:** #398 (parent #183) · **Route:** spike (deliverable = this findings doc; no code changed).

## Question

This session's `forge:autopilot` runs saw the Claude Code auto-mode classifier deny some in-session merge attempts and not others, in a pattern no earlier ticket fully characterized. Two sub-questions block AC.1/AC.2:

1. **Is there a real, recoverable pattern** in which merge attempts get denied vs. allowed?
2. **Is a denial detectable in-process** — can `merge.mjs`/`watchdog.mjs` observe it at all (a distinguishable exit code/stderr), or does it only ever manifest as the calling agent's own turn stopping on a permission-block message the script never receives?

## Findings

Two of the eight examples cited in the ticket brief (#380/#379, #399/#403) carry **explicit, first-person denial narration** in their trail comments — the rest do not, despite the brief's framing suggesting they all did. That gap is itself a finding (see "What did not corroborate," below).

**What the evidence supports:**

- Only **two** of the examples (#380, #403) carry explicit, contemporaneous or post-hoc first-person denial narration. Both required, per the agent's own words, an **explicit fresh in-session grant** before the retry succeeded — not merely the passage of time, not merely switching who issued the command.
- **#380's own text refutes the cleanest form of the "subagent vs. main loop" hypothesis (candidate (a) in the ticket).** The comment says the classifier denied *both* the delivery subagent's *and* the main loop's own first attempt. If invocation source alone determined the outcome, the main loop's own retry should not have needed a fresh grant too. It did.
- **#403's comment is consistent with, but does not independently confirm,** a subagent-denied/main-loop-succeeded split — it never states which context issued the successful retry, only that "a fresh grant" preceded it. Given #380 shows a fresh grant was the actual precondition (independent of invoker), the more parsimonious read of #403 is the same mechanism: a fresh grant, not a change of invoker, is what cleared it.
- **#397 is a true negative control for "awaiting-merge always means classifier denial."** It didn't — it was GitHub branch protection, and the agent explicitly said so rather than assuming classifier involvement. That distinction matters: not every merge friction point in this session's history is the phenomenon #398 is about.
- **Candidate (c), raw `gh pr merge` vs. the sanctioned `merge.mjs` bar:** SKILL.md (`§ Auto-merge`, line 143) already states raw `gh pr merge` is "NOT the sanctioned path" for autopilot tickets. The one denial that names the invocation explicitly (#380) names it as **`merge.mjs` itself being denied** (*"when invoking merge.mjs --ship --gates --reviewer --security for PR #380"*) — i.e., going through the sanctioned bar did **not** protect it from denial. That refutes "just use merge.mjs instead of raw gh pr merge" as a fix; both this session's real denials were on the sanctioned path.
- **Candidate (b), time elapsed since the last user message:** not verifiable from git/gh artifacts at all (see "What did not corroborate"). The wall-clock gaps recovered here range from ~2 minutes (clean, no denial) to ~22.6 hours (unconfirmed, crosses a session boundary) to ~7-8 minutes (confirmed denial-then-grant). Elapsed time alone does not separate the confirmed-denied cases from the confirmed-clean ones — #380 and #403 both cleared in under 10 minutes, the same order of magnitude as the clean #391/#404 cases.

**What did not corroborate (honest gap):** the #398 driving ticket's own brief asserts denials on #384 (as a "bad-faith retry" for a raw `gh pr merge`) and #394 (a subagent attempt denied, requiring a fresh grant). Neither issue/PR comment thread, nor the GitHub event timeline, contains any text supporting those specific characterizations — no comment mentions "bad-faith," a raw `gh pr merge` attempt, or a denial at all on either ticket. This is not proof those denials didn't happen — GitHub artifacts only capture what an agent chose to *narrate into a trail comment*, and #403 shows that even a confirmed denial is sometimes only narrated after the fact, in the merged-comment, with no separate real-time record. But it means those two specific claims are **not independently verifiable from anything queryable in this repo** — they would have existed, if at all, only in the live session transcript, which is not persisted anywhere this spike can read. Reporting them as confirmed data points (as the driving ticket's brief did) would have been inventing certainty AC.1 explicitly disallows.

**Bottom line on AC.1:** the only clean, corroborated signal recoverable from real evidence is **"the harness auto-mode classifier evaluates merge authorization per attempt, not once per session or by invocation source, and an explicit fresh in-session grant is what clears a denial"** — which is exactly what `merge.mjs`'s own top-of-file comment and `SKILL.md`'s Resume protocol section already assert (both predate this spike, evidently written off the #397/#380 experience directly). This spike's timeline **independently corroborates** that existing claim rather than discovering a new, more specific rule. No sub-pattern (subagent-vs-main-loop, raw-gh-vs-bar, elapsed-time threshold) survives contact with the full evidence set — each candidate has at least one confirmed counter-example above.

### AC.2 — in-process detectability

**Finding: not detectable in-process, and this session's own evidence is consistent with that.**

Reasoning, grounded in the actual code paths:

1. **A real subprocess-level failure *is* observable and already handled.** `merge.mjs`'s `runMerge` shells out via `ctx.gh(['pr', 'merge', ...])`; when that `gh` invocation fails (bad auth, merge conflict, branch protection), it returns a non-zero result the script inspects: `if (!merged.ok) return { ok: false, error: merged.stderr || 'gh pr merge failed' }` (`plugin/scripts/autopilot/merge.mjs:83-84`). **#397/#402 is the real, confirmed example of this path** — the agent parsed `reviewDecision=REVIEW_REQUIRED` off `gh pr view` and correctly reported it as a policy gate, "not a classifier denial." This class of failure is already fully detectable and already produces a real exit code (`process.exit(1)`, line 107).
2. **The harness auto-mode classifier is a different layer entirely.** Per the two confirmed denial cases (#380, #403), the denial is narrated by the agent as a **tool-invocation-level block** ("Merge blocked by the Claude Code auto-mode classifier") — it happens *before* `node merge.mjs` (or the equivalent `autopilot_merge` MCP call) is dispatched at all, not as a failure return from a dispatched process. Confirming evidence: no trail comment anywhere in this session's history — including the two confirmed-denied cases — quotes an exit code, a stderr string, or any script-parseable value for the denial. Every mention of a classifier denial is agent prose, written after the agent's own turn was blocked by the harness, never a value merge.mjs's own error-handling branches could have produced. If the denial were subprocess-observable, at least one of the eight trail threads reviewed would show it being parsed like #397's branch-protection block was; none do.
3. **This is not a new conclusion — the code already encodes it, and this spike is the first to test it against real data rather than assume it.** `merge.mjs:13-24`'s own top comment states: *"There is no code-level way to detect this in advance today (tracked separately, #398)."* `SKILL.md`'s Resume protocol section (line 225) says the same: *"There is no code-level way to predict this in advance (#398)."* Both were apparently written off the #397 experience, before this spike ran. This spike's contribution is confirming that claim against the fuller, cross-referenced evidence set (AC.1's table) rather than taking it on faith — and it holds up: nothing in the corroborated timeline contradicts it.
4. **Bash `node .../merge.mjs` vs. MCP `autopilot_merge` — no confirmed behavioral difference, but also no confirmed comparison.** Every denial this session's evidence actually names is phrased as *"invoking merge.mjs --ship --gates --reviewer --security"* (#380) — CLI-flag shaped, i.e. a Bash-tool invocation, not the MCP tool's structured call syntax. No trail comment in the reviewed set names a denial (or a clean pass) through the `autopilot_merge` MCP tool specifically, so this spike **cannot empirically confirm** whether the two transports are classified differently. By harness design as best understood from this evidence, both are tool-invocation-layer objects gated by the same auto-mode classifier *before* either the shell subprocess or the MCP server's handler code runs — so a denial on either path should be equally invisible to the underlying script (`merge.mjs`'s `runMerge` function is identical code regardless of which transport calls it; it never runs at all when denied, regardless of transport). This is a reasoned inference from the architecture, not a directly observed data point, and is flagged as such rather than asserted as fact.

## Recommendation

**No code-level detection is possible — recommend keeping this prose-level, with one small, honest refinement.**

Because AC.2 confirms a classifier denial never reaches `merge.mjs`/`watchdog.mjs` as a distinguishable signal, proposing a `denied`/`classifier-blocked` *mechanically detected* outcome type in `watchdog.mjs` (as the ticket's spike scope floats as an option) is not viable — there is no script-observable input to key it off. The existing prose mitigation already in `SKILL.md`'s Resume protocol and `merge.mjs`'s top comment — *stop, surface the denial to the user, ask for a fresh explicit in-session grant, do not blindly retry* — is what AC.1's evidence actually supports as correct: both confirmed denials (#380, #403) cleared only after an explicit fresh grant, and #380 shows that switching the invoking context (subagent → main loop) alone was **not** sufficient, so a rule like "the main loop should always be the one to invoke the final merge, not delegate it to the subagent" (the candidate the ticket brief hints at) is **not supported by the fuller evidence** and should not be adopted — it would not have prevented #380's denial, since the main loop's own first attempt was also denied there. This also means there's no real tension with `SKILL.md`'s "the subagent merges within the same invocation" design (§ Orchestration) to flag: that design isn't implicated as a cause, so it doesn't need to change.

**The one concrete, additive refinement this spike recommends:** the current prose mitigation is stated as *loop-level* guidance ("the loop's only recourse is ... stop, surface, ask"), but the loop can only react to what a subagent *chooses to report*. Nothing today distinguishes "an ordinary escalation" from "I was denied by the classifier" in the subagent's returned `{issue, outcome, pr, notes}` contract (`watchdog.mjs`'s `resolveReturnedTicket` — `plugin/scripts/autopilot/watchdog.mjs:32-92` — has exactly three outcomes: `continue`/`escalate`/`merge`, none named for this). #403's own trail history illustrates the risk: the denial there was only narrated *after* the eventual successful merge, in the merged-comment — had the retry *not* succeeded, there would have been no distinct signal telling the loop "this one hit the classifier, don't treat it like a generic stall." Recommend briefing every delivery subagent (in the delivery brief, § Orchestration) to recognize the classifier's denial language explicitly and return a **self-reported**, distinct outcome string (e.g. `outcome: 'classifier-denied'`) rather than folding it into the generic `awaiting-merge`/`escalated` buckets — and giving `watchdog.mjs` one more `case` to route that specific string to a `surface + do-not-retry + request fresh grant` action, distinct from a generic escalation's messaging. This is a **self-report contract**, not detection: the code never infers the denial from any process signal (AC.2 rules that out); it only trusts and routes a value the *agent itself* recognized in its own blocked turn and chose to report. That keeps the fix at the correct layer, matches this session's own working pattern in the two confirmed cases, and gives the loop (and future spikes) a persisted, structured record instead of relying on whether an agent happens to narrate the denial into a trail comment at all.

This is a **prose + narrow plumbing** recommendation, not a code change — no implementation is included in this spike per its scope; the above is left for a follow-up ticket if the owner agrees it's worth the small `watchdog.mjs` surface addition.
