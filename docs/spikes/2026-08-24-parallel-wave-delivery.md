# Spike — is parallel wave delivery + a serialized merge train worth breaking autopilot's one-ticket-at-a-time invariant?

**Date:** 2026-08-24 · **Ticket:** #508 (parent #503) · **Route:** spike (deliverable = this findings doc; **no parallel-delivery or merge-train code is touched by this branch's diff** — the spike branch never merges).

## The question and the decision it feeds

The 2026-08-15 insights report proposed replacing autopilot's sequential delivery with fan-out: predict each ready ticket's touched files, build a conflict graph, deliver file-disjoint tickets in parallel, and feed green PRs into a single serialized merge train. That is a direct challenge to a deliberate design invariant — `plugin/skills/autopilot/SKILL.md:20`: *"One ticket at a time (v1). Finish and merge one before starting the next — no worktree machinery, no cross-ticket conflicts."* `docs/specs/2026-07-21-forge-autopilot.md` §9 names the same thing as "future: parallel (deferred, designed-for)," not built in v1. The decision this spike feeds is the owner's: keep the invariant, break it, or narrow the break — not this ticket's to make (per its own AC-508.5 and the spike route generally).

**Retriage (2026-08-24) sharpened the question with fresh evidence** the 2026-08-15 report predates: this run measured its own GraphQL cost and pause behavior for the first time. AC-508.3 requires this doc to confront that evidence directly, not soften it.

## Grounding methodology

Every claim below is checked against real repo state: `.forge/autopilot/run.json` (read directly), `plugin/scripts/autopilot/ledger.mjs` and `ratebudget.mjs` (read in full), `gh issue view`/`gh pr list` for the tickets and PRs named, and the prior spikes this one builds on (`docs/spikes/2026-08-06-autopilot-concurrency-safety.md`, #387; `docs/specs/2026-08-08-github-resilience.md`, whose own §"the owner's stated cause — parallel mode — is not actually the mechanism" finding is directly relevant background). Where a number could be independently reconstructed from a persisted artifact, it was — and the specific derivation is shown. Where a number in AC-508.3's own text could **not** be independently reconstructed from anything this session can read (`run.json` keeps only a 6-reading rolling window, `ledger.mjs:33`; there is no separate pause log), that is stated plainly rather than presented as independently re-verified. This mirrors the discipline the two referenced prior spikes (#519, #475) both used.

## 1. Directly verified: the shared GraphQL budget, not serialization, is what this run's own telemetry shows binding

`.forge/autopilot/run.json`'s `rateBudgetReadings` (a 6-entry rolling ring buffer, `MAX_BUDGET_READINGS = 6` at `ledger.mjs:33`) holds, in order: `[4999, 2158, 4999, 2498, 4999, 4673]`. Running `ledger.mjs`'s own `recentBudgetDeltas` logic by hand (only *positive* consecutive drops count — a reading that goes back up means the hourly window reset, not that a ticket was free, `ledger.mjs:132-147`) over these six readings gives exactly three real deltas: **2841, 2501, 326**. The MAX of those — **2841** — is precisely the "evidence-based low-water threshold ~2841" this ticket's retriage cites, independently reconstructed here from the persisted ledger rather than taken on trust. That number is real, and it is exactly what `estimateTicketCost()`'s unknown-kind path (`ratebudget.mjs`) would derive right now for the next ticket, since `KIND_COST_ESTIMATES` (`{docs: 975, spike: 3457}`) has no entry for the board `type` vocabulary that every real ticket carries (`item`/`bug`/`test`/`epic` — confirmed by reading the table and its own docblock, which explains why: #462 and #438 are both type `item` and differ 5x in measured cost, so no `item`-keyed estimate is safe).

`run.json`'s `outcomes` array independently confirms the one-ticket-at-a-time shape and its actual throughput this run: `iterations: 14`, but only **11 outcome entries** — 8 reached `merged` (#490, #556, #557, #555, #561, #562, #506, #507), 2 reached `escalated` at the triage stage (#484, #497), and this ticket (#508) itself reached `triage: ready`. That 14-vs-11 gap is not a discrepancy to wave past: `applyOutcome` (`ledger.mjs`) increments `run.iterations` on *every* call but dedups `run.outcomes` by issue, last-write-wins — so an issue that was recorded once as `stalled-before-pr` (the return-then-resume watchdog's non-conforming-report outcome, #464/#474/#522) and later superseded by a resolved outcome for the same issue costs 2+ iterations but leaves exactly one visible outcome entry. This exact pattern is independently attested elsewhere in this repo's own history — the archived prior run's own outcome note for #517 reads *"Took 4 delivery attempts (3 return-then-resume stalls)"* (`.forge/autopilot/run-archived-20260823.json`) — so the most likely explanation for this run's 3-iteration gap is the same stall class, not an unexplained loss of data. This is directly relevant to the concurrency question in §4: a stall that costs extra iterations but not extra *visible* outcomes today would, under N-concurrent delivery, need the ledger to correctly attribute those extra attempts per-issue while N other issues are also mid-flight — sharpening rather than resolving the concurrency question. `mergeMode` is `auto-merge` throughout. Timestamps on the merged outcomes show two very different regimes: a dense stretch (#556→#562, then #506→#507) landing every ~20–38 minutes apart, and two much larger gaps — ~13.5 hours between #490 (04:39 UTC) and #556 (18:09 UTC), and ~2h17m between #562 (20:04:39) and #506 (22:22:10). **What `run.json` can and cannot tell us here needs to be kept separate:** the dense, ~20–38-minute cadence is consistent with delivery being dominated by CI wait + adversarial-review rounds rather than by "waiting for permission to start the next ticket" — there is no idle gap of that size visible between back-to-back merges in that stretch, which is direct partial evidence for AC-508.2 Q1 (see §2). The two large gaps are *consistent with* rate-budget pauses (an hourly reset only refills to 5000, so a pause deep in a window can stretch well past the ~25-minute worst case `esc-526-msvi7329` describes) but **this session cannot independently attribute either specific gap to a budget pause versus something else (a session boundary, human unavailability) from `run.json` alone** — the ledger records outcomes and a 6-reading budget window, not a pause-event log. This is an honest gap in what's reconstructable, not a claim either way.

**AC-508.3 also names two figures this doc cannot independently re-derive from anything persisted in this checkout**: a single full delivery measuring "~1578 GraphQL points," and "eight budget-driven pauses across eight merged tickets in one run (including one hard-zero mid-ritual that cut a post-merge step short and needed manual cleanup)" — AC-508.3's own text, verified directly against `gh issue view 508`, names **no specific ticket number** for that hard-zero event. A separate, non-ticket source available to whoever scoped this spike additionally associated the hard-zero with #561 specifically; this doc checked that association rather than assuming it — `#561`'s own board comments (its ticket trail, read in full) describe an unrelated fix (`autopilot/SKILL.md` sitting 2 bytes under a size gate), with no mention of a rate-limit event anywhere in its trail. **That #561 attribution could not be confirmed from anything in the tracker and should be treated as unverified, not as fact** — if the hard-zero happened, it happened as an operational event during the run's live execution that no ticket's own trail was the place to record, and `run.json`'s 6-reading ring buffer, by construction, cannot retain evidence of a pause count or a specific incident from earlier in a 14-iteration, ~20.5-hour run — only the last six checks survive. **These two figures (and the hard-zero event's existence, independent of which ticket it's attached to) are accepted here as reported by whoever scoped this spike, not independently re-derived** — the distinction matters because AC-508.2/508.3 require evidence, not estimates, and the honest position is: the *mechanism* and *order of magnitude* (a single ticket's cost measured in the low thousands, comparable to or exceeding the 2841 figure this doc did independently confirm) are corroborated by what's reconstructable; the *exact* figures, and the #561 attribution specifically, are not re-derivable from this checkout's persisted state within this time-box.

**Bottom line for AC-508.3's direct question: yes, the shared account-wide GraphQL budget — not ticket serialization — is what this run's own reconstructable evidence points to as the binding throughput constraint.** The one number this doc verified independently (2841, the MAX of three real consecutive-check drops) is on the same order as a single ticket's full cost per the ratebudget.mjs cold-start fallback (`DEFAULT_LOW_WATER = 4993`, itself "the empirically measured worst-case single-ticket GraphQL cost," per its own docblock, from #438: "4995 -> 2 remaining"). A 5000 pt/hr bucket where one ticket alone can cost half to nearly all of it is a tight constraint independent of whether tickets are delivered one at a time or ten at a time — and running tickets concurrently does not create more bucket. It draws down the *same* bucket faster, not slower: N parallel deliveries multiply concurrent board reads, PR-status polls, and review-round GraphQL calls against one 5,000-point account-wide hourly ceiling that has no per-process partition.

## 2. To answer, Q1 — wall-clock lost to serialization vs. CI/gate waits

Per §1's dense-stretch reading, the seven back-to-back merges this run completed (#556 through #507, excluding the two large gaps — five transitions: 21.3, 27.4, 32.0, 34.9, 38.4 minutes apart, recomputed directly from `run.json` timestamps) landed 20–38 minutes apart with no visible idle gap attributable to "waiting on the previous ticket to finish before this one may start" — the loop's own design (`SKILL.md` § Cost & context: *delegate, don't inline*) means ticket N+1's selection is a cheap script call (`select.mjs` — "plain scripts (zero model cost)," per `SKILL.md`:303) that happens the moment ticket N's outcome is recorded, not after some additional serialization delay. **The evidence available in this run does not show a distinct "serialization tax" separate from CI-wait and adversarial-review-round time** — the per-ticket wall-clock in the dense stretch looks like it *is* CI + gate-round time, not CI + gate-round time *plus* an added queueing cost. This is the single most direct piece of evidence against the premise that parallelism buys meaningful wall-clock: if the thing eating the 20–38 minutes is CI checks and reviewer/security rounds (both of which would still have to happen per-PR under a parallel-wave design, just concurrently), parallel waves shorten wall-clock only to the extent CI/review time overlaps across tickets — and a serialized merge train (by design, one PR lands at a time, "rebases, re-verifies" per ticket) reintroduces exactly the same per-PR CI/verify wait at the far end, just moved from before delivery to after it. **Not fully settled in this time-box:** whether CI wait specifically (as opposed to review-round wait) dominates the 20–38 minutes — that would need per-phase timestamps this run's trail comments don't consistently carry, and reconstructing it precisely was judged not worth the GraphQL cost of pulling every PR's check-run history for a half-day-boxed spike.

## 3. To answer, Q2 — is touched-file prediction trustworthy enough for a conflict graph?

Two blockers, one already found by a prior spike and reconfirmed here, one newly checked against this repo's live config:

- **Shared-file collisions are structurally invisible to a scoper-based, area-disjointness check.** `docs/spikes/2026-08-06-autopilot-concurrency-safety.md` (#387, finding C) already demonstrated this concretely: that spike's own deliverable touched `docs/README.md`'s route index — a file nearly every docs-adding ticket touches regardless of its "real" area — and the same is true of any shared index/lockfile/config surface. **This spike's own PR will touch the same route index file** (§ Follow-ups), which is a live, present-tense instance of exactly the class of file spec §9's "non-overlapping blast radius via the scoper" line doesn't account for. Two file-disjoint-by-area tickets can still collide at merge time on these surfaces; a conflict graph built purely from per-ticket blast radius would not catch it.
- **The `forge-graph` MCP tooling this ticket's own body names (`blast_radius`) is not turned on for this repo today.** `.claude/forge.json` has no `features` block at all, and `plugin/scripts/doctor.mjs:222` states the consequence directly: *"tsconfig.json found but features.graph is off — graph-RAG (find_component/who_uses/blast_radius/reuse_candidates) is available for this repo"* (i.e., available-but-off). A conflict graph built on `blast_radius` predictions would need that feature turned on and its predictions validated against real merge conflicts first — neither is true today, so the premise of Q2 (can prediction be made "trustworthy enough") is currently unanswerable from a standing start, not merely unanswered.
- **Cost of a wrong prediction, reasoned from what's already known rather than measured:** a false "disjoint" verdict that turns out wrong surfaces at merge-train rebase time as a real conflict needing manual/automated resolution mid-train — which is exactly the shared-file-collision risk above, now hitting the merge train instead of being caught pre-delivery. No instance of this was observed this run (parallel delivery isn't running), so this is reasoned risk, not measured cost.

## 4. To answer, Q3 — orchestrator context under N-concurrent, given #466

**Correction against an earlier draft of this section:** #466 is not open. `gh issue view 466` shows it **CLOSED**, merged via PR #468 (`97c83a6`), and its own merge receipt states the fix directly: *"`select.mjs`'s four spawnable loop actions (resume/deliver/triage/shape) now all get the same orchestrate-only spawn discipline #156 previously gave delivery alone — the `--shape` route no longer runs `forge:shape` inline in the main window."* So the specific defect #466 named — `shape` running inline in the main orchestrator window, driving it to 100% context — is fixed, not open, and the *"main context unchanged — ~O(1) per ticket"* guarantee (`SKILL.md` § Cost & context) is now uniformly enforced across all four loop actions, not just `deliver`. This changes what Q3's honest answer actually is: there is no longer an open, code-confirmed defect to point to as evidence the discipline is fragile.

What #466's fix *does* still leave open, reasoned rather than measured: per-ticket delivery context is O(1) by construction (a discardable spawned subagent per ticket, now uniformly true for all four actions) — but that says nothing about the *orchestrator's own* bookkeeping as N grows. Today the orchestrator reconciles exactly one "one-line outcome" at a time; a design that fans out N concurrent delivery subagents multiplies that to N outcomes, N sets of monitor heartbeats (`forge-ci`, `forge-agents`), and N watchdog relays in flight simultaneously, per wave. Whether that stays cheap (N small, independent one-line reconciliations) or compounds (cross-referencing N in-flight tickets' state to avoid conflating them) is genuinely unmeasured — no N-concurrent run has ever happened in this repo — `grep -ri worktree plugin/` returns a few incidental hits today (`SKILL.md`'s own "no worktree machinery" line, unrelated mentions in `learn/distill.mjs` and `release/readiness.mjs`), but confirmed fresh here, none of them are worktree-pool or concurrent-delivery code, matching #387's own finding that no such machinery exists — so the honest answer is: **the #466-shaped risk this doc originally reached for is resolved, not open; the orchestrator-bookkeeping-at-N question is real but unmeasured, and weaker evidence than this section first claimed.**

**A second, more concrete and previously undocumented blocker found while re-verifying #387's findings for this spike:** #387 (2026-08-06) identified that `.forge/autopilot/run.json`'s read-modify-write pattern (`ledger.mjs`'s `recordOutcome`/`recordFiled`/`recordBudgetReading`/`recordConvergence`/`startRun` — all read-the-whole-file, mutate in memory, write-the-whole-file, with no lock across the gap) causes a genuine lost-update race under concurrent writers, and recommended shipping an exclusive-create lockfile (`.forge/autopilot/run.lock`) as the near-term fix. **That lockfile primitive now exists** — `plugin/scripts/lib/lock.mjs`, built for #414's outbox, whose own docblock explicitly credits #387's design ("`readLock`... per #387's design... never implemented anywhere until this ticket") — **but it was wired only into `lib/outbox.mjs`, not into `ledger.mjs`.** Grepping `plugin/scripts/autopilot/*.mjs` and `SKILL.md` for `lock.mjs`/`acquireLock` today finds zero hits inside `ledger.mjs` itself. So the exact race #387 found and reasoned through in detail — two processes each reading the same `run.json` snapshot, each computing a "new" state from it, the second write silently discarding the first's recorded outcome, which directly weakens the runaway backstop (`guardTripped`/`nextIteration` read `run.iterations`) — **is unresolved today**, nearly three weeks and dozens of merged tickets after it was found and a general-purpose fix for it shipped for a different consumer. This is the single most concrete, load-bearing prerequisite gap for parallel wave delivery found in this spike: N concurrent delivery subagents each calling `recordOutcome` would corrupt the ledger from the first wave, deterministically, using code that exists in this repo right now. Filed as a follow-up (§ Follow-ups) rather than fixed here, since fixing it is not this spike's deliverable and the fix's actual value is independent of whether parallel waves are ever built (it also protects against the *already-possible*, already-observed-as-a-report accidental-concurrent-hand-launch scenario #387 was originally filed to investigate).

## 5. To answer, Q4 — does a serialized merge train survive the per-attempt classifier and the rate budget?

**Classifier (#397/#398):** both are closed (#397: doc-fix, closed 2026-08-08; #398: spike, closed 2026-08-08) — but closed means the work landed, not that the underlying evidence stopped applying. #397 documents, with real examples from production runs, that the Claude Code auto-mode classifier evaluates merge authorization **per attempt, not once per session** — a later merge in the same, uncompacted session can be denied even after an earlier merge in that same session succeeded, with no code-level way to predict which (#398's own closed spike confirmed a denial isn't detectable in-process at all — it blocks the tool call before any script runs, so there's no exit code or stderr to key off). `SKILL.md` § Resume protocol carries the corrected language today, citing #397 directly, confirming this is settled, documented behavior, not an open question. A serialized merge train, by construction, needs ONE agent's merge authority to survive **N consecutive merge attempts** in sequence (rebase → re-verify → merge, repeated per queued PR) rather than the ONE attempt today's one-ticket-at-a-time model needs per ticket. Given #397's own evidence that even two attempts in one session aren't reliably both-granted, a merge train doesn't relocate this wedge to a cheaper place — it **concentrates** it: every ticket in the wave now shares the fate of whichever attempt in the train first gets denied, where today a denial affects exactly one ticket. This is a straightforward, evidence-grounded "worse, not better" finding, not a guess.

**Rate budget:** the merge train's own described work — rebase, re-verify, retry-on-backoff, per PR — still calls `gh` against the same shared bucket every real merge already does today (CI status polls, the merge call itself, board writes). A merge train does not create new budget; it schedules the *same* per-PR GraphQL draw serially at the back end, after N parallel deliveries have already drawn on the bucket **concurrently** at the front end. §1 already establishes that concurrent draw against a shared, unpartitioned hourly ceiling is the mechanism that makes parallelism a throughput risk, not a throughput win, on this evidence — the merge train doesn't change that; if anything, queuing N re-verify-and-retry cycles behind a shared bucket that a bad estimate can already stall for up to an hour (per `esc-526-msvi7329`'s own worst case) means a stalled merge train can now block N tickets' landing at once instead of one ticket's.

## 6. To answer, Q5 — is there a narrower win that keeps the invariant?

Two candidates, both grounded in what already exists rather than proposed fresh:

- **Parallelizing only the review/CI wait for the ticket already in flight is not a new idea to evaluate — it's the *existing*, already-shipped design.** `docs/spikes/2026-08-17-synchronous-adversarial-passes.md` (#475, merged) already examined exactly this seam from the opposite direction (whether to *remove* the existing reviewer+security concurrency) and recommended *keeping* the nested, concurrent spawn-and-await pattern (`execute-agents/SKILL.md`: reviewer and security already run as two concurrent passes over one ticket's diff, not serially). So "parallelize the review/CI wait, not delivery" is not a narrower version of this ticket's proposal to design — it is today's status quo, already delivering the parallelism available within a single ticket's own gate without touching the one-ticket-at-a-time invariant at all.
- **A genuinely narrower, not-yet-built option:** since §1–§5 together locate the actual bottleneck in the shared GraphQL bucket rather than in wall-clock serialization, the highest-leverage "narrow win" available is not parallelizing delivery at all — it's the work already scoped and open on the board to shrink what a single delivery costs (#528, reduce per-ticket GraphQL consumption) and to get real per-`type` cost evidence so the conservative MAX-based low-water threshold can stop pricing every ticket as the worst-ever-seen one (#531). Both directly relieve the constraint this spike's own evidence says is binding, without inheriting the ledger race (§4), the shared-file-collision gap (§3), or the merge-train classifier risk (§5) that a real parallel-wave design would take on.

## 7. Related open work (AC-508.4)

- **#528** — "reduce per-ticket GraphQL consumption (continues #407 AC.2/AC.3)": open, not a hard blocker for this spike's own conclusion, but directly relevant — if #528 lands and meaningfully shrinks per-ticket cost, the §1 finding (one ticket can already cost half the hourly bucket) weakens, and the case against parallelism weakens with it. This is exactly the kind of evidence that should trigger a re-look, not a reason to wait to answer this spike now.
- **#531** — "gather real per-board-type GraphQL cost evidence, then populate `KIND_COST_ESTIMATES` for the type vocabulary": open, same relationship — real per-type evidence would let the budget gate stop treating every real ticket (`item`/`bug`/`test`/`epic`) as worst-case, which is orthogonal to whether delivery itself is parallelized but changes how tightly the shared bucket actually binds.

Neither is a prerequisite this spike needed to wait on to answer its own question — the evidence in §1 is sufficient on its own — but both bear directly on whether a future re-ask of this same question would land differently.

## 8. Recommendation

**Decline, for now — the one-ticket-at-a-time invariant should hold.** This is the owner's decision to make, not this ticket's; the reasoning below is offered as the basis for that call, not as an autonomous change.

Why decline rather than pursue or pursue-narrowed:

1. **The binding constraint this run's own reconstructable evidence points to (§1) is the shared, account-wide GraphQL bucket, not serialization.** Parallel waves draw on that same bucket concurrently rather than serially — they make the actual bottleneck worse, not better, exactly as this ticket's retriage warned.
2. **No wall-clock evidence supports the premise that serialization itself is the wasted time (§2).** The dense-stretch cadence this run produced looks like CI-plus-review time, which a merge train's own "rebase, re-verify" step reintroduces per PR regardless of how delivery was parallelized.
3. **Two concrete, code-level prerequisite gaps exist and are unfixed today**, independent of the budget question: the ledger's lost-update race (§4 — a general-purpose fix exists in this repo, `lib/lock.mjs`, and was simply never wired to `ledger.mjs`) and the shared-file-collision gap in blast-radius-based disjointness (§3, reconfirmed live by this very spike's own PR touching the route index). Both would need to be closed before a parallel-wave design could be trusted, regardless of the budget math.
4. **The classifier's per-attempt behavior (§5) makes a serialized merge train strictly riskier than today's model**, not merely different — it concentrates N tickets' merge fate behind one agent's authority surviving N consecutive attempts, where #397's own evidence says even two attempts in a session aren't reliably both-granted.

**What would change this answer:** real, measured evidence that #528 has shrunk per-ticket GraphQL cost enough that concurrent draw against the shared bucket is no longer the dominant constraint, combined with #531's real per-type cost evidence replacing today's worst-case-MAX estimate. Until then, re-proposing fan-out parallelism would be re-litigating a question this spike already answered from evidence, not opening a new one — which is the reason this reasoning is recorded here rather than left to be rediscovered.

**Not recommended even as a narrowed pursue:** the one already-narrow form worth having (concurrent reviewer+security within a single ticket's own gate) is not new work — it already shipped, and is described in §6.
