# Spike — autopilot concurrent-run safety + parallel-mode feasibility (#387)

**Date:** 2026-08-06 · **Ticket:** #387 (parent #183) · **Route:** spike (deliverable = this findings doc; no code changed).

## Question

An owner report (2026-08-05) said *"the parallel mode when I enable that got a lot of issue."* `plugin/skills/autopilot/SKILL.md:20` and `docs/specs/2026-07-21-forge-autopilot.md` §9 both confirm parallel execution is **not built** in v1 — there is no flag, config field, or worktree-pool code path (`grep -ri worktree plugin/scripts/autopilot` returns no hits). The owner's exact repro (what was "enabled," how many concurrent invocations, what broke) was **not captured before this spike started** — per the ticket's own AC.4, that is noted here as a limitation rather than invented. Given no real toggle exists, the most plausible mechanism is **running two or more `autopilot` sessions by hand against the same repo**. Three questions: (A) does the ledger actually race under that condition, with code proof; (B) what's the cheapest real guard; (C) is spec §9's deferred worktree-pool design closer or further away than it reads, now that autopilot has run for real this session.

## Findings

### A — the ledger race is real: confirmed, not corruption, but a genuine lost-update race

`plugin/scripts/autopilot/ledger.mjs` owns `.forge/autopilot/run.json` (one file per repo, `RUN_RELPATH` at line 13). Every mutator follows the same shape: **read the whole file, compute a new value in memory, write the whole file back** — a classic read-modify-write with no lock anywhere in the path.

- `loadRun` (lines 40–42) → `readRun` (lines 25–38) does a plain `readJson`.
- `recordOutcome` (lines 112–116): `const run = applyOutcome(await loadRun(cwd), entry); await writeJson(join(cwd, RUN_RELPATH), run);` — read, mutate, write, with no lock held across the gap.
- `recordFiled` (lines 117–121) is the identical shape for the `filed` array.
- `startRun` (lines 131–145) also reads first (`const existing = await readRun(cwd);`) and only writes a fresh run if nothing exists — two processes racing at run start can each see "nothing exists" and each write a `freshRun`, the second clobbering the first's `startedAt`/`mergeMode`/`mergeReason`.

**The good news: `writeJson` (`plugin/scripts/lib/jsonfile.mjs:31-43`) is genuinely atomic** — it stages bytes in a sibling `*.pid.random.tmp` file and `rename`s it onto the target, so a crash mid-write can never leave truncated/interleaved JSON (this was hardened for #164, and `readRun`'s `SyntaxError` fallback at ledger.mjs:35 is belt-and-suspenders for exactly that case). **So the corrupted-JSON half of the original hypothesis is refuted** — two processes writing at literally the same instant will not produce garbled JSON.

**What does go wrong is a lost update.** Sequence: process A calls `recordOutcome({issue: 100, outcome: 'merged', ...})` and process B calls `recordOutcome({issue: 200, outcome: 'escalated', ...})` for a *different* ticket, interleaved as: A reads run.json (`iterations: 5`) → B reads run.json (`iterations: 5`, same snapshot) → A computes `iterations: 6` + appends #100's outcome → A writes → B computes `iterations: 6` + appends #200's outcome (from its stale snapshot, which never saw A's write) → B writes, **overwriting A's entire write**. The persisted file ends up with `iterations: 6` (should be 7) and only #200's outcome — #100's merge is **silently dropped from the ledger** even though it genuinely happened (the PR is really merged, the ticket really moved to `done` on the board; only the *loop's own record of it* vanishes). This corrupts two things that matter:

1. **`renderReport`** (ledger.mjs:96-109) — the end-of-run summary — under-reports what actually happened.
2. **`guardTripped`/`nextIteration`** (ledger.mjs:66-94) — the runaway backstop compares `run.iterations` against `boardSize × factor`. A lost-update race under-counts iterations, which *weakens the exact safety rail* (spec §8, SKILL.md "Loop backstop") that's supposed to catch a pathological runaway — precisely in the concurrent-run scenario where a runaway is most likely, since two loops can each pick and re-pick tickets the other has already actioned.

Beyond the ledger file itself, concurrent loops have **no cross-run awareness of ticket selection**: `select.mjs`'s `selectNext` (lines 48-60) reads the live GitHub board fresh each call, so two processes calling it near-simultaneously can both see the same `ready` ticket and both select it before either has moved it to `inProgress`. Both would then spawn a delivery subagent for the same issue — at minimum duplicated work and a wasted branch-creation collision inside `forge:deliver`, at worst two independently-generated PRs against the same ticket where the second to reach the merge bar has to rebase over the first's already-merged change (mechanically survivable, since `ship`'s rebase step exists for this, but wasteful and confusing, not "designed for"). **Conclusion: refute the "corrupted JSON" framing, confirm the "lost update / silent state drop" framing** — this is real and demonstrable from the code, not assumed.

### B — a lockfile is the right minimal guard; nothing like it exists in forge yet to reuse

Searched `plugin/scripts/lib/` and all of `plugin/scripts/autopilot/` for any existing lock/PID/mutex idiom (`grep -n "process\.pid|mutex|exclusive|already running|acquireLock|isRunning"`). The only real hits are unrelated: `jsonfile.mjs`'s `process.pid` used purely to make a temp-file name unique, and prose strings like "work in progress." **There is no lock/mutex pattern anywhere in forge to reuse or mirror.** The closest analogous idiom is `board/escalate.mjs`'s pending-decision marker file (`.forge/decisions/<id>.json`, `status: 'pending'|'resolved'`, lines 90-94/119) — but that's a *record of a fact* for a human to resolve, not a mutex that blocks concurrent access; it doesn't fit this problem directly, though its "one JSON file, `status` field, `writeJson`" shape is a reasonable template for a lock file's *contents*.

Recommended shape, cheap and cross-platform (Windows + Linux, per forge's own requirement):

- **`.forge/autopilot/run.lock`**, containing `{ pid, startedAt, hostname }`.
- **Acquire with an exclusive create, not `writeJson`.** `writeJson`'s temp-then-`rename` pattern is correct for *updating* state but wrong for *acquiring a lock* — it always succeeds and clobbers. The correct primitive is `fs.open(path, 'wx')` (or `writeFile(path, data, { flag: 'wx' })`), which atomically fails with `EEXIST` if the file already exists. This flag is supported identically on Windows and POSIX (Node's libuv layer maps it consistently on both); nothing in forge currently uses it, but it is a small, dependency-free addition alongside `jsonfile.mjs`, not a new library.
- **Release on natural stop** (try/finally around the loop, plus a `SIGINT`/`SIGTERM` handler) — mirrors how `ledger.mjs`'s own resume protocol already assumes clean-Ctrl-C is the common case (SKILL.md § Stop conditions: "Interrupt: Ctrl-C between tickets is clean").
- **Stale-lock detection is not optional — a hard kill (crash, `kill -9`, machine sleep/power-loss) leaves the lock file behind with no process left to clean it up.** Two checks, combined (single-signal checks are each individually unreliable):
  - **Liveness:** `process.kill(pid, 0)` throws `ESRCH` if the pid is dead; this is a documented, cross-platform Node idiom (no signal is actually delivered with `0`, on either POSIX or Windows) — but a **stale PID can be reused by an unrelated live process** after enough time/reboots, so liveness alone can produce a false "still running."
  - **Age bound:** combine with the lock's own `startedAt`, the same wall-clock-proxy idiom `docs/spikes/2026-08-05-session-window-detection.md` already used for `run.json`'s `startedAt` (and that `sessionpause.mjs` treats a too-old on-disk snapshot as stale rather than trustworthy). A lock older than a generous ceiling (e.g. the same ~5h session-window order of magnitude) is treated as abandoned regardless of what the PID check says, and reclaimed with a loud warning rather than silently.
- **Scope and honesty:** this is a **local filesystem lock**, not a distributed one — it only protects "two processes on this machine, this repo checkout, at the same time." That is exactly the scenario the owner's report plausibly describes (multiple hand-launched sessions), so it is the right-sized fix; it is explicitly not a claim to solve multi-machine or networked-filesystem races.

This is small, additive, and testable in isolation the same way `preflight.mjs`/`sessionpause.mjs` are (a pure decision function — "is this lock acquirable/stale?" — plus a thin IO wrapper), consistent with how every other autopilot safety mechanism in this codebase is built.

### C — spec §9's worktree pool: further away on the blocker it names, closer on one it doesn't

Read `docs/specs/2026-07-21-forge-autopilot.md` §9 in full. It is three sentences: v1 is sequential "by owner choice"; the loop is "factored so a bounded worktree pool... can replace the single-ticket step **without changing the merge bar, the escalation model, or the run ledger**"; not built in v1. That "without changing... the run ledger" claim is the spec's own stated assumption about what parallelism would require — and finding A directly contradicts it: **the run ledger cannot safely be touched by more than one process today, at all**, accidentally or by design. That is a bigger and more concrete blocker than anything spec §9 names (it doesn't mention the ledger as a risk in either direction), and it is not a "some day" concern — it is the *first* thing that would break, deterministically, the moment two worktree-pool workers both call `recordOutcome` in the same run. **So on the piece the spec explicitly waves through, this spike finds the feasibility read should be more cautious than the spec states, not less** — a lockfile (finding B) blocks *accidental* concurrent runs, but a real worktree pool needs the ledger itself made concurrency-safe (e.g. per-ticket lock around the read-modify-write, or a compare-and-swap write, or moving to one-file-per-ticket-in-flight reconciled at pool-drain) — a real design task, not a "no changes needed" given.

A second blocker the spec doesn't name at all, found by reading this session's own working set rather than the spec: **non-overlapping blast radius (the scoper-based check the spec leans on) doesn't cover shared "index" files** — this very ticket's own deliverable touches `docs/README.md`'s route index, which nearly *every* docs-adding ticket touches regardless of what area it's otherwise scoped to; the same is true of things like `uv.lock`/`package-lock` or a shared config file. Two worktree-pool tickets that are genuinely non-overlapping by the scoper's area-based definition can still collide on these shared surfaces at merge time. The spec's "chosen for non-overlapping blast radius via the scoper" line (§9) doesn't account for this class of file at all — it's a real gap, not a restatement.

One thing this spike found that's **closer** than the spec assumed, because it postdates the spec: this agent's own environment now exposes `EnterWorktree`/`ExitWorktree` tools and an `Agent` tool `isolation: "worktree"` mode — harness-level primitives for exactly the "run a subagent in an isolated git worktree" mechanic spec §9 imagines forge would have to hand-build. `grep -ri worktree plugin/` turns up zero usage of either anywhere in forge's own code today, so this is unexploited, not adopted — but it means the "how do we even get N isolated worktrees with clean lifecycle" mechanical question, which used to be the obvious first engineering lift, may now be substantially assisted by the harness itself rather than something `plugin/scripts/autopilot/` needs to reimplement from raw `git worktree` calls.

Net assessment: **further away than the spec suggests on the ledger (its stated "no changes needed" is wrong), and it doesn't mention the shared-file collision risk at all** — both are real, unaddressed blockers found by reading the current code rather than the spec's prose. **Closer than the spec assumed on the pure worktree-isolation mechanics**, because the harness has grown a relevant primitive since the spec was written, that forge hasn't looked at yet. The honest read is: don't build §9 next. Build the lockfile (B) first — it's small, fixes a real and *currently reachable* hazard (accidental concurrent hand-launches), and forces the ledger's concurrency-safety questions to get answered in miniature (one lock, not N-way coordination) before committing to the much larger worktree-pool design.

## Recommendation

1. **Ship the lockfile guard (finding B)** as the near-term fix: `.forge/autopilot/run.lock`, exclusive-create at run start, PID+age staleness check, released on clean stop. This is scoped, cheap, cross-platform, and directly addresses the plausible mechanism behind the owner's report (concurrent hand-launched sessions) without inventing the unreproduced specific repro.
2. **Do not treat spec §9 as ready to build.** Its "the run ledger needs no changes" premise is refuted by finding A; a real worktree pool needs the ledger's read-modify-write made concurrency-safe first (this is new design work, not a config flag), plus a shared-file collision story the current scoper-based non-overlap check doesn't cover. Recommend keeping §9 deferred, but revise its own text to drop the "without changing... the run ledger" claim — it's inaccurate as written, independent of whether/when the pool gets built.
3. **Genuinely open for the owner:** the owner's exact repro was never captured (per AC.4, noted rather than invented) — if/when it resurfaces, comparing it against finding A's specific failure mode (a dropped/under-counted ledger entry, or a duplicate delivery on the same ticket number) would confirm or redirect this diagnosis with real evidence instead of the plausible-mechanism inference this spike relies on.
