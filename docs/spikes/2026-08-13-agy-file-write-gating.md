# Spike — does forge's `run_command`-only PreToolUse matcher leave file writes safely unhooked, or dangerously unhooked, on agy? (#436)

**Date:** 2026-08-13 · **Ticket:** #436 (parent #182) · **Route:** spike (deliverable = this findings doc + the AC.5 docs update; **no production-source changes** — `plugin/hooks/*.mjs` and `plugin/scripts/agy/emit.mjs` are untouched by this branch).

**agy version tested: 1.1.12** (`agy --version`, Windows, this machine). The 2026-08-12 spike (`docs/spikes/2026-08-12-agy-approval-semantics.md`) tested v1.1.7 and recorded ADR-0007's "(c)" rule to re-check at the next build bump — this spike is that re-check, and it surfaces one version-relevant regression (§5).

## The question

`plugin/scripts/agy/emit.mjs:121-132` (`buildHooksConfig`) scopes both `forge-safety` and `forge-capture` to `matcher: 'run_command'`. The 2026-08-12 spike proved the narrowness is forge's own choice — a scratch `"*"` matcher blocked a native `write_to_file` call — so file writes/edits are completely unhooked on agy today. Widening looks mechanical, but two open questions block treating it as one: does agy's host-level 10s fail-open hook timeout (also found by the 2026-08-12 spike) get materially worse once the hook fires on *every* tool call, not just shell commands; and does agy already have some *other*, independent gate on file writes the way it does on `run_command` (`permissions.allow`, `command(<target>)`), which would change whether any forge-side change is even needed. This spike does not decide whether to widen — see Non-goals — it gathers the evidence the eventual decision needs.

## Grounding methodology

A scratch plugin was built for this spike outside the forge repo tree (`%LOCALAPPDATA%\Temp\claude\C--mywp-forge\e22bb796-15b6-458b-81ba-491606d00cfd\scratchpad\436-spike\`, not part of this branch): `.agents/hooks.json` registering a matcher-`"*"` `PreToolUse` hook (`.agents/hooks/pretool.mjs`) that reads a **decision** and a **sleep-ms** value from control files (so the same rig re-runs under different conditions without touching `hooks.json`), logs every invocation's tool name, `stepIdx`, argument keys, and its own processing duration to `invocations.log`, then replies with the configured decision. Driven headlessly via `agy --print "<instruction>" --add-dir <scratch> --mode accept-edits`, cross-checked against `~/.gemini/antigravity-cli/cli.log` for hook-level pass/fail events the hook's own log can't see (a killed hook process never reaches its own logging line). `--dangerously-skip-permissions` was tried once and refused outright by the Claude Code auto-mode classifier on this session — not retried, per the operating rule against working around a safety classifier — so every result below is from **plain headless mode**, no permission bypass.

**One setup snag worth recording because it later became a finding (§5):** the scratch hook's command was first written quoted, matching `emit.mjs`'s own style (`node "hooks/pretool.mjs"`). That failed outright — see §5. All of AC.1/AC.2's results below use an **unquoted** command (`node hooks/pretool.mjs`), which is scratch-rig-only and not a statement about how `emit.mjs` should be fixed (out of scope here).

## AC.1 — hook-timeout blast radius when the matcher fires on every tool call, across a representative session

**Reconfirmed: fails open, and reproducibly so across multiple calls and multiple tool types, not one worst-case probe.**

Baseline (hook responds fast, `sleepMs: 0`): three sequential `write_to_file` calls in one session, `hookDurationMs` 7-9ms each, decision honored trivially (`allow`). Negligible overhead — widening the matcher costs nothing when the hook is healthy.

**Below the configured `timeout: 10` (8s sleep, `decision: deny`):** one session where the agent's plan involved four different gated tool calls — `write_to_file`, a `run_command` fallback, `list_dir`, `view_file` — every one completed in ~8.0-8.02s and **every one was correctly denied**: no file written, no command run. The `"*"` matcher treated all four tool types identically; nothing about widening past `run_command` changed the below-timeout behavior.

**At/above the timeout (15s and 25s sleeps):** fail-open reproduces, but the exact cutoff is **not a clean, deterministic 10s boundary** in this build — recorded honestly rather than rounded to a tidy number:

- An **isolated single-call** session (`decision: deny`, `sleepMs: 15000`, one direct "write this file, don't check anything first" instruction) is the cleanest evidence: `cli.log` shows exactly one event — `pre-tool hook failed: JSON hook "jsonhook__scratch-436_PreToolUse_0_0" failed: command failed: exit status 1` — no corresponding line in the hook's own `invocations.log` (the process was killed before it reached its own logging statement, which sits after the sleep). The file **was written anyway**, despite the hook being configured to deny it. This is the write-tool-call analogue of the 2026-08-12 spike's `run_command` finding, now confirmed for `write_to_file` specifically.
- Repeating that exact isolated single-call shape at `sleepMs: 25000` with `decision: deny` produced the same result (mtime of the written file lines up to the second with a `pre-tool hook failed: exit status 1` event in `cli.log`).
- **But** a `sleepMs: 25000`, `decision: allow` isolated single call *did* run to completion (`hookDurationMs: 25023`, `completed: true` in the hook's own log) rather than being killed at ~10-13s. And a multi-call session with `sleepMs: 15000` and `decision: allow` had **all six** gated calls (three `write_to_file`, plus others) complete their full 15s sleep (total session wall time ≈ 90s = 6 × 15s almost exactly) rather than any being cut short.
- A noisier multi-call session (`decision: deny`, `sleepMs: 25000`, an instruction that made the agent explore with `list_dir`/`view_file` before writing) showed **both** behaviors in the same run: three hook invocations completed their full 25s sleep and had `deny` honored (logged normally), while `cli.log` separately recorded **five** `pre-tool hook failed: exit status 1` events spaced roughly 10-13s apart, one of which lines up with the file actually getting written despite `decision: deny`.

**Conclusion for AC.1:** the fail-open behavior the 2026-08-12 spike found for a single `run_command` probe is real, reproduces across a representative multi-call session, and — critically for this ticket — **reproduces identically for `write_to_file`** once the matcher is `"*"`, with no special-casing observed for the non-shell tool. What this spike adds beyond re-confirming the direction: the actual kill/fail-open trigger is **not a precise, always-exactly-10-seconds cutoff** — it behaves more like a race that sometimes lets a slow hook run to completion and sometimes doesn't, clustering loosely in the 10-15s range but not reliably. That is a *more* concerning finding than a clean deterministic timeout would be: a rule author cannot reason about "the hook has exactly 10 seconds" as a hard contract, only "under ~8s is safe, at or above the configured timeout is a coin flip that sometimes lands on silently running the tool anyway." Widening the matcher to include `write_to_file` does not change *whether* this failure mode exists — it existed already for `run_command` — but it does widen *how often* a slow hook's answer can be silently discarded, because every additional tool type now depends on the same fragile margin.

## AC.2 — does agy have its own native approval gate for `write_to_file`, independent of forge's hook?

**No — not observed, in contrast to `run_command`'s confirmed native gate.** Three converging pieces of evidence:

1. **With forge's hook present (`decision: allow`), headless `write_to_file` succeeds with zero extra prompting or denial**, needing neither `--dangerously-skip-permissions` nor any `permissions.allow`/`command(...)`-style entry in `~/.gemini/antigravity-cli/settings.json` (confirmed empty of any such entries for this test — see the file's contents in Sources). This is the same headless mode where `run_command` is **hard-denied** by default with the CLI's own runtime message pointing at `permissions.allow` (reconfirmed here on v1.1.12, matching the 2026-08-12 spike's v1.1.7 finding verbatim: `jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for, so it was auto-denied...`).
2. **With `hooks.json` removed from the scratch project entirely** (no forge hook, no scratch hook — nothing intercepting `PreToolUse` at all), a fresh headless `write_to_file` call still succeeded immediately, no prompt, no denial. The equivalent test for `run_command` with `hooks.json` also removed still produced the identical `"command" permission... auto-denied` message — proving `run_command`'s gate is independent of any hook (it fires with zero hooks installed), while `write_to_file` has no analogous independent gate to fire.
3. **No shipped documentation names a permission surface for file-write/edit tools.** `hooks.md`'s only documented permission-string grammar is `command(<target>)`, used for `run_command`; a grep across every shipped `agy-customizations`/`antigravity_guide` doc for `permission`/`allow`/`approve` (same doc set the 2026-08-12 spike grepped) turns up nothing naming `write_to_file`, `edit`, or a file-scoped equivalent.

**Bottom line for AC.2:** unlike `run_command`, which sits behind two independent gates (forge's hook, plus agy's own native `command` permission wall that the 2026-08-12 spike documented), `write_to_file` in headless mode currently sits behind **zero** gates once forge's hook is out of the picture (as it is today, being unmatched). This is stated as an observation for the eventual policy decision, not a recommendation: it means the "is a forge-side change even necessary" question from the ticket's framing resolves to **yes, if any gating is wanted at all** — there is no fallback native layer to lean on the way there arguably is for shell commands. Whether *interactive* (non-headless) agy sessions show a native prompt for file writes was not directly observed (the same "not independently observed" honest gap the 2026-08-12 spike recorded for `run_command`'s interactive case) — but headless mode's total absence of any denial path, contrasted with `run_command`'s hard denial in the identical setup, is itself strong structural evidence there is no equivalent gate, not merely an absence of a prompt this rig can't render.

## AC.3 — candidate rule shapes for a non-command payload (proposed, not chosen)

`write_to_file`'s args, confirmed empirically from the hook payload (`toolCall.args` keys: `CodeContent`, `Description`, `Overwrite`, `TargetFile`), are a **path, a content blob, an overwrite flag, and free-text metadata** — not a command string. `denylist.mjs`'s regex-on-argv rules (and the tokenize-then-judge design in `docs/spikes/2026-08-13-argv-tokenize-model.md`) answer structural questions about shell argv; none of that machinery reads a path+content pair. Four candidates, evaluated against `denylist.mjs`'s own stated scope discipline ("a TARGETED backstop... NOT a general destructive-command sandbox," `plugin/hooks/denylist.mjs:4-15`) — **no winner picked here; that is a follow-up/owner decision (see Non-goals).**

**A. Path-based denylist on `TargetFile`.** A small, fixed, component-anchored list of catastrophic target patterns (`.env`, `.ssh/`, `id_rsa`/`id_ed25519`, `credentials.json`, `.git/hooks/`) — the same component-anchoring discipline `SAFE_RM_TARGET` already uses, just as a deny-list of dangerous names instead of an allow-list of safe ones. *Fit:* closest in spirit to the existing rules — purely structural (string component matching), no content parsing, cheap and synchronous. *Tradeoff:* narrow by construction (matches the file's own "targeted, not exhaustive" philosophy) — it does nothing for a catastrophic write to a path *not* on the list, e.g. overwriting `package.json`'s `scripts` block. That gap is arguably acceptable under the guard's own stated non-goal of being a "general... sandbox," but it should be named explicitly if adopted, not discovered later as a surprise.

**B. Overwrite-of-protected-config rule.** Block when `Overwrite: true` **and** the target matches a short list of paths that grant execution/CI trust (`.github/workflows/*.yml`, `hooks.json`, `.claude/settings*.json`, lockfiles). *Fit:* mirrors the existing `hard-reset`/`force-push` framing — "destructive to state that already exists" rather than "creates something new." Still purely structural (flag + path, no content parsing). *Tradeoff:* this is the candidate most likely to violate the guard's own false-positive discipline — routine, legitimate edits to `package.json`/CI workflow files are extremely common, and this repo's own denylist history (`docs/spikes/2026-08-13-argv-tokenize-model.md` §4) is explicit that a false positive here "trains people to route around the guard." Scoping it tightly (which sub-paths, which keys) is real design work this spike does not attempt.

**C. Content-signature rule on `CodeContent`.** A small set of structural, RCE-shaped patterns being *introduced* by the write — a new executable shebang line inside `.git/hooks/`, a CI workflow step combining `pull_request_target` with an untrusted checkout, a `postinstall`/`preinstall` script key added to `package.json`. *Fit:* the closest analogue to the existing pipe-to-shell/eval-of-substitution rules, which are also about RCE shape rather than raw destructiveness. *Tradeoff:* this is the one candidate that requires actually parsing file content (YAML/JSON/shell-script bodies), not argv — a materially larger, more open-ended surface than anything `denylist.mjs` does today, and the #448 brace-expansion spike's own lesson (an unbounded-cost scan over attacker-controlled text produced a 4.65s ReDoS through this exact hook family) applies directly to scanning arbitrary-length `CodeContent`. Of the four, this is the one most likely to *become* "a general... sandbox" by accretion if not deliberately bounded.

**D. No new rule — matcher widening alone, or accept the gap.** Widening `hooks.json`'s matcher to `run_command|write_to_file` (or `"*"`) **without pairing it with any of A-C** changes nothing observable: `agy-deny.mjs`'s current logic has no file-write-shaped rule to consult, so every `write_to_file` call would still resolve `allow` — the only change would be added fail-open surface per AC.1, for zero gating benefit. *Fit:* this is the necessary zero-baseline the other three are weighed against, and — echoing the argv-tokenize spike's "don't do it at all" option (§6 there) — remains a legitimately defensible position: nothing here is currently *worse* than before #436 was filed (file writes were always unhooked), and the guard's own file header already disclaims being a security boundary.

## AC.4 — does the evidence support widening the matcher, and what's the smallest safe next step? (conclusion, not a commitment)

**Widening the matcher alone is not useful, and could be actively counterproductive, without a paired rule.** Candidate D's baseline observation is the load-bearing one: `agy-deny.mjs`'s default is `allow` for anything it has no specific rule for, so a bare `"*"` matcher change produces zero new gating and strictly increases the fail-open surface AC.1 measured (every additional tool type now shares the same non-deterministic ~10-15s margin). **The evidence does not support widening the matcher as a standalone change.**

Whether widening is worth doing *at all*, once paired with a real rule, is the policy question this spike is explicitly not allowed to answer (Non-goals) — but the evidence does say something about *sequencing*: AC.2 found `write_to_file` has no fallback native gate the way `run_command` does, which is a real argument for *some* forge-side coverage being worth an owner's attention (there is currently nothing between an agy-hosted session and an arbitrary file write, forge hook or otherwise). AC.3's four candidates span from "cheap and narrow" (A) to "requires real content parsing and risks scope creep" (C) — mirroring exactly the phased-commitment lesson `docs/spikes/2026-08-13-argv-tokenize-model.md` §5-§6 already learned on this same hook file: don't commit to the whole shape before the cheapest piece is scoped.

**Smallest safe next step:** the owner picks one candidate from AC.3 (or explicitly ratifies option D — "accept the gap," which is a legitimate answer, not a non-answer) as a scoped, Phase-1-sized design/implementation ticket; **only that ticket** — not this spike — pairs a matcher widening with the chosen rule, in one change, so the two never ship independently (a widened matcher with no rule is worse than the status quo per the paragraph above). Filed as **#477** (see Sources), explicitly scoped to "decide + design," not a blank check for implementing all of A-C.

## §5 — unplanned finding: a `hooks.json` command-quoting bug currently breaks forge's own installed hooks on Windows/agy 1.1.12 (filed separately, out of scope here)

Not an AC of this ticket, and not folded into any AC's conclusion above, but too significant to leave unreported (the 2026-08-12 spike set the precedent of filing an out-of-scope critical finding — #434 — rather than silently dropping it, and this spike does the same rather than quietly deleting the setup snag that surfaced it).

While building the scratch rig, the **first** version of `.agents/hooks.json` used a quoted command string matching `emit.mjs`'s own style exactly: `"command": "node \"hooks/pretool.mjs\""` (relative, quoted — the current, post-#307 `emit.mjs` shape, not the older absolute-path style). That failed outright: `cli.log` recorded `Cannot find module 'C:\...\436-spike\.agents\"hooks\pretool.mjs"'` — the literal `"` characters leaked into the path Node tried to resolve, rather than being stripped as shell quoting. **The same failure, independently, was already present on this machine's real global forge plugin install** (`~/.gemini/config/plugins/forge/hooks.json`, a stale dogfood install using an older absolute-path format) — its `forge-safety` hook failed with the identical `MODULE_NOT_FOUND`-on-embedded-quote pattern during the very first smoke test of this spike, before the scratch rig was even touched. Switching the scratch hook to an **unquoted** command (`node hooks/pretool.mjs`, safe only because the scratch path has no spaces) resolved it, which is why every AC.1/AC.2 result above used that form.

This means: on this Windows machine, running agy 1.1.12, **today's exact `emit.mjs`-generated `run_command` hook command may not execute at all**, failing closed-looking-like-open (the process errors, agy's fail-open default kicks in per AC.1, and the command runs *unchecked* rather than checked-then-allowed) — a materially different and more severe failure than "narrow matcher." This was not exhaustively root-caused (which shell layer mishandles the quotes, whether it's Windows-cmd-specific, whether it reproduces on a fresh clean install rather than this dev machine's history) — that is real follow-up work, not something to hand-wave here. Filed as **#478** (see Sources), a bug, not folded into #477's scope, because it is orthogonal to the matcher-width question this ticket is about: it would be just as severe with the matcher staying `run_command`-only.
